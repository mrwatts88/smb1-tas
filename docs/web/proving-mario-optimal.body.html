Chapter 01

The size of the thing

A speedrun is not a performance. It is a list of button presses, one entry per frame, and the game is a function that turns that list into an ending.

The NES runs at 60.0988 frames per second, and exactly once per frame the game reads the controller. So a run of Super Mario Bros. is a list of 17,868 rows, each row saying which buttons are held. HappyLee's record is such a list. Ours would be another one.

For moving Mario, only four buttons matter: A, B, Left, Right — sixteen combinations per frame. (Up and Down matter only at pipes and vines; Start and Select do nothing useful mid-level.) Tool-assisted rules allow Left and Right at the same time, which the real game handles in a strange and very useful way: your facing direction stops matching your moving direction, and Mario decelerates instantly.

Sixteen choices per frame, compounding. A single 150-frame stretch of one room has 16150 possible input sequences — a number with 181 digits. There are not enough atoms in anything to enumerate that.

Two things are visible there, and the whole project lives between them.

The good news: most of those sequences are duplicates. Press Left then Right, or Right then Left, and the machine can end up in literally the same condition — same position, same speed, same everything. Once two histories produce an identical state, they are interchangeable forever after, and we only need to keep one. That is the single fact that makes any of this possible.

The bad news: collapsing duplicates only bought a factor of about 3.5 in that measurement. The state count still multiplies by roughly five every frame. Deduplication alone gets you six frames into a two-thousand-frame level. Everything else in this document is about the second lever: throwing away states that provably cannot win.

Chapter 02

The clock is a staircase

Before you can search for a faster run, you have to know what "faster" even pays. In this game, usually nothing.

When you touch the flagpole, the level does not end. A fixed sequence starts: the slide, the walk into the castle, the timer counting down at one unit per frame, the flag raising, a fade. And the last wait in that chain is gated by a counter that only ticks over once every 21 frames — the same global counter the whole game runs on.

So the level's contribution to your final time is rounded up to a multiple of 21. Reach the flagpole three frames earlier and, almost always, the game ends at exactly the same frame. You have to cross the boundary.

Why this changes the search itself

Because the payoff is a threshold, we never ask the search to "minimise time". We ask a yes/no question: can you be at this spot by frame N? That converts every state into something checkable — if a state provably cannot make frame N, it and its entire future can be deleted immediately. A minimising search has no such licence. The deadline is the pruning.

Chapter 03

The thing we search is not an emulator

An emulator is a faithful machine and a hopeless search node. The search runs on a reimplementation of Mario's physics that keeps a few dozen bytes and throws away the rest of the NES.

We do own a real emulator, and it matters: a headless build of the QuickNES core, running the actual ROM, about 15,000 frames per second. That is our ground truth. But a saved state of it is 12,792 bytes — CPU registers, both RAM banks, PPU memory, sprite tables, mapper state. Multiply by the forty million states a single frame-layer can hold and the arithmetic ends the conversation.

So the search runs on a model: smb-opt, a Rust reimplementation of Super Mario Bros.'s player physics that MrWint hand-extracted from the game's disassembly in 2017. It does not emulate a CPU. It runs the same arithmetic the game's routines run, on a struct that holds only the variables that can affect the future:

The level itself is not in the state at all — it is a fixed grid of blocks compiled in ahead of time. Neither are the score, the music, the sprites, the palette, or the CPU. None of them can change what Mario does next.

The payoff is roughly a thousandfold speedup, and states small enough to sort tens of millions of them at a time. The cost is that the model is a claim about the game rather than the game — which is what the next chapter is about.

What we changed

The tool we started from was built for a different job: short hand-chained segments, solved with a best-first search, enemies ignored entirely. Our patch is 3,836 lines across 28 files, and it falls into four groups.

  • Physics corrections. Each of these was a real divergence from the game, found by testing rather than by reading: the run cap persisting for ten frames after B is released; a jump requiring A to have been released the previous frame; the block-bounce timer; the rule that blocks the joypad above the screen applying only in water levels; coins ending the block-collision routine early; the exact order in which Mario's hitbox is built relative to background collision.
  • More of the game in the state. Block states — a bumped block is a special tile for about fourteen frames and then a used tile, which means a bumped hidden block becomes a platform and a mid-bounce cell blocks a wall-walk. The 4-2 lift, a moving platform. And a full enemy module for 4-2: the three-goomba group, the koopa and the buzzy beetle including shells and kicks, and three piranha plants that every previous description of that level had simply missed. That module is what grew a search record from 24 bytes to 96.
  • A different search. Frame-layered breadth-first over all sixteen inputs, with layers spilled to disk, replacing an in-memory best-first search over a reduced input set (see chapters 05 and 10).
  • New bounds and new goals. A height-aware bound (chapter 08), a coupled bound for the warp zone, and the ability to search for "be at this spot, at this height" instead of only "finish this level".

Chapter 04

Proving the engine before trusting the answer

A search over a wrong model returns a confident, worthless number. So every part of the machinery has its own test, and each test has to be able to fail.

1 · Does the model step like the game?

Pick a starting frame. Generate input sequences — purely random ones, mutations of the record's own inputs, and sequences steered to make interesting things happen (a stomp, a kick, a death). Run each one through both the emulator and the model. Compare Mario's position, sub-pixel, speed, speed fraction, y position, y speed, y fraction and state on every frame; with enemies, compare every slot's flag, id, state, position, speed, force, direction and timers too.

The 4-2 enemy module currently stands at 5,787 trials, 877,058 compared frames, zero differences — including 1,825 deaths on the identical frame, 3,686 stomps and 949 kicks with matching aftermaths. That number only sounds like a formality if you skip the history: the first run of this test on the borrowed physics model diverged on 53 of 200 trials. Every physics correction listed in the last chapter came out of a difftest failure.

2 · Do the rules match the actual recording?

We have every byte of the NES's RAM for all 17,868 frames of HappyLee's run. So a new rule — say, how enemies spawn — gets written as a small independent simulator and required to reproduce the dump exactly: all 588 frames of 4-2's main area, every enemy slot field, plus the level parser's internal offsets.

A test that cannot fail proves nothing

So each of those checks ships with negative controls: deliberately break one rule and the same test must break too. Three perturbed variants of the enemy spawn law fail by 119, 20 and 63 mismatching rows respectively — which is what licenses us to believe the zero.

We learned this the hard way. One admissibility audit reported a clean sweep for an afternoon before we noticed it had been silently vacuous: the trace was stopping at the first item bump, so no trajectory ever reached the goal and there was nothing to check. The rule now: a result of "zero problems found" is suspicious until you know how many things were looked at.

3 · Is the pruning honest?

The bound that lets us delete states (chapters 06 and 08) is a mathematical claim: from here, you cannot possibly reach the goal in fewer than h frames. If it ever overstates by even one frame, the search will delete the true optimum and then report a confident, wrong proof. So bounds are audited like theorems: fly thousands of random trajectories, and at every frame where the goal is later reached at frame t′, assert that t′ − t is at least the bound claimed at frame t. The x-bound has survived 1,906,600 such checks; the height-aware bound about 1.6 million, including stomp-heavy trajectories. Zero violations each — and three genuine bugs found in a single afternoon before that was true.

4 · Did the last change break anything?

Every engine change is followed by a regression control: rerun a known small search and require the layer sizes to come out identical — 6, 16, 34, 70, 134, 673, 3,472, 16,472, 69,489, 257,001, goal at layer 10. Not "similar". Identical. This is also how a second machine proves it built the same engine before it is allowed to contribute anything.

5 · And then the answer itself

Finally, no result counts until it has left the model. A finished search prints a winning state; that state is traced backwards through the layer files to recover the actual button presses; those presses are appended to the record's own prefix and replayed on the real emulator, frame against frame, field against field. The four segments solved so far replayed 149/149, 315/315, 333/333 and 415/415 frames identical. A path that has not been replayed is not an answer.

Chapter 05

Why breadth-first, and why that is not a style choice

One property of this problem decides the algorithm: every move costs exactly the same.

Press buttons, one frame passes. There is no cheaper move and no more expensive move — a frame is a frame. In search terms, every edge in the graph has weight 1.

That makes breadth-first search not merely convenient but exactly right. Layer k of a breadth-first search is precisely the set of situations reachable in k frames. So the first layer at which a winning state appears is the optimum, by construction. No priority queue, no tie-breaking, no reopening nodes, no proof obligation beyond "we searched layer k−1 and it wasn't there". Dijkstra and A* exist to cope with edges of unequal cost; here they would be breadth-first search wearing a costume.

So the engine walks frame by frame. It reads the entire set of states for frame k, applies all sixteen button combinations to each, and writes the resulting set for frame k+1. Between those two steps sit the two things that keep the set from exploding.

Deduplication, and one subtlety that matters

Two states are the same if their compressed keys are identical, and the layer is deduplicated by sorting it — sorted order gives you duplicate-removal for free while merging, which matters enormously once the layer lives on disk.

The subtlety: we deduplicate within a layer, never globally. It is tempting to keep one big "already seen" set, and the original tool did. But in a level with enemies, Mario standing at the same spot with the same speed at frame 200 and at frame 210 is not the same situation — the goombas have walked, the level parser has advanced, the interval clock has a different phase. A state reached at a later frame is a different node of the search, full stop. Global deduplication is only sound in a room with no frame-dependent anything, and getting that wrong would silently delete correct answers.

We also expand all sixteen inputs, every frame. The tool we inherited used a hand-written rule set to skip "pointless" inputs — B only while moving that way, Left+Right only when standing, A only when a jump could start. That is a 20× speedup and it is probably harmless. But "probably" is not a proof, and the entire point of this exercise is proofs, so we pay the 20×.

Chapter 06

The bound: the only thing that really prunes

Deduplication removes copies. The bound removes futures.

Here is the whole idea in one line. For a state, let g be the frames already spent, h be a guaranteed-not-too-large count of the frames still needed, and D be the deadline we are testing. If g + h > D, this state cannot possibly reach the goal in time, so delete it — and with it every sequence that would ever have started from it.

Everything hinges on getting h from somewhere. Our workhorse is a precomputed table with a neat trick behind it.

The x-table

Horizontal motion in Super Mario Bros. depends on surprisingly little: the current x speed, its absolute value, the moving direction, the facing direction, whether Mario is on the ground, and whether the run flag is set. Call that the x-class. There are only tens of thousands of them — a space small enough to enumerate completely.

So before the search starts, we run a small exhaustive search on that tiny space alone, computing for every x-class the maximum distance Mario could possibly cover in exactly k frames. That gives "frames needed to reach x ≥ X" as a table lookup. It is admissible, because it ignores walls, gravity and enemies, all of which can only slow you down. And it is tight within its own world, because the value is actually achieved by some sequence of x-classes.

Two rules we do not bend

  • Admissible or bust. A bound that overstates by a single frame can delete the true optimum and then let the search announce a proof that is simply false. This is why bounds get audited with millions of assertions before they are trusted, and why a bound that "seemed obviously right" has three times turned out to have an off-by-one in it.
  • Relaxations may cheat, but only in Mario's favour. Every bound is really a fantasy version of the game where Mario is allowed to do more than he can — no walls, landings on surfaces he could not really stand on, head bumps whenever convenient. Anything impossible in the fantasy is impossible in reality. Cheat the other way and you get the failure we hit early on: a bound assuming Mario accelerates as fast as possible on the ground pruned every single state at the first frame — because in this game Mario accelerates faster in the air, with a doubled adder, which is exactly what the record does.

The trick we deliberately refuse. The obvious extra prune is dominance: if two states are alike but one is further right, drop the other. In most games that is free. Here it is false. Wall clips, the flagpole glitch and the block-edge tricks the whole route depends on turn on exact sub-pixel values — being one sub-pixel further right can be the difference between clipping into a wall and bouncing off it. Any dominance rule here needs a per-case proof, and that is filed as future work rather than assumed.

Chapter 07

Slack is the price you pay

The cost of proving something is not set by the length of the segment. It is set by one number: how much room the search has to be wasteful.

Define slack as the deadline minus what the bound says is needed at the very first state. Slack 0 means we are asking "can you do it in exactly the minimum the physics allows?" — and then the search is a corridor: almost anything that dawdles for even one frame is immediately over budget and deleted. Slack 15 means fifteen frames of freedom to wander, and the number of ways to wander for fifteen frames is astronomical.

This law dictates the working method, which we call the ladder: always try the tightest possible deadline first, then loosen by two, then two more. Tight rungs are cheap and get cheaper the tighter they are; loose rungs are unaffordable. That is the exact opposite of how you would guess a search should be scheduled.

Why the tightest rung gives the strongest possible answer

Set the deadline equal to the bound. Now consider any state that lies on some path reaching the goal in fewer frames than the deadline: its g + h can never exceed that shorter length, which is below the deadline, so it can never be pruned. Nothing on a shorter path can be lost. Therefore if the search finds the goal at layer D, no shorter path exists — the answer is the movement bound, and it is proven, in a single run, with no lower rung needed.

Three of the four segments solved so far came out this way, on the first rung.

And a rung that finds nothing is a result too, not a failure. When a deadline of 147 frames died out at layer 29, that established that 147 is impossible for that segment — which is half of the eventual proof that the answer is exactly 149.

Chapter 08

Teaching the bound to see height

The x-table has one enormous blind spot: it has no idea Mario is in the air.

The segment that broke it was innocuous: reach x ≥ 339 while at or above height 112 — get up on top of the pillar in 4-2's main room. The x-table looks at that and says "137 frames", because it only ever sees the horizontal part. It does not know that being up there also requires a jump you must commit to before you arrive, and that if you are airborne and falling you are simply not allowed to be higher for a while.

That is not a theory; it is what the logs said. With the x-only bound and a deadline twelve frames above it, the frontier sat at 13 million states per layer from layer 75 onwards, reached 23 million by layer 100, and the furthest state in it had covered 215 pixels of the 339 needed. Loosen the deadline to 28 above the bound and it doubled every single layer from the start. The search was drowning in altitude.

The height gate

So we built a second bound that does the opposite of the first: it runs the game's vertical rules exactly — the jump's initial velocity, the lighter gravity that applies only while A is held, the fact that releasing A is irreversible, head bumps, the snap that happens on landing — and throws away horizontal motion, except at one place where the two must meet: surfaces.

A surface is the top of a cell you could stand on, together with the range of x where a foot would actually be on it. Then, for any state, the bound reasons like this:

  • while airborne, holding A gives the highest trajectory possible — releasing or bumping only ever makes you lower — so "could I be above the goal height at frame k without landing?" is a simple window;
  • for each surface, the earliest frame you could land on it is whichever comes later: the vertical arrival, or the x-table's estimate of getting a foot over it;
  • from standing on a surface, a precomputed table gives the minimum frames to reach the goal height by chaining jumps and landings through higher surfaces;
  • and the bound is the first frame count where the x-table permits the horizontal goal and the height is reachable.

Like every bound it is deliberately generous — it permits one-frame landings on wall faces, and head bumps on any rising frame, both of which the real game restricts. Generous is the safe direction: the bound may only ever understate the time required.

What it did

The same segment, same deadline, with the height term switched on: the frontier peaked near 40 million around layer 105, fell to 14.4 million by layer 120, and then collapsed — one layer turned 14.3 million parents into 1.7 million survivors and threw away 210 million children. The last layers ran in twenty seconds each. The goal appeared at layer 149 and at no earlier layer.

Segment S1 is exactly 149 frames, and 147 is impossible. That is the first machine-proven statement about this room that anyone has.

Chapter 09

Segments, and the seams between them

We cannot search a whole level. So we cut it up — and every cut is both the thing that makes the search affordable and the place a better answer could be hiding.

A level is 1,700 to 3,000 frames long. Our segments are 80 to 190. We pick milestones — "get up onto the pillar", "get to the end of the top surface", "get across the lift pit" — and solve each one exhaustively, starting from where the previous one finished.

4-2, the main room — the level we are searching right now

solid bricks / blocks hidden block segment milestone enemy

Each segment result is honest: exhaustive, deadline-tight, replayed on the emulator. But look closely at the join.

The seam, stated plainly

Segment 1 explored an entire room of possibilities and found roughly 45 million different ways to arrive at its milestone on the optimal frame. Segment 2 begins from one of them — picked by a rule of thumb, "highest speed, then furthest right".

Which means:

  • The chain's total is a real, playable input sequence, so it is a genuine upper bound on the level. It is not a proof of the level's optimum.
  • An arrival that is one frame slower but in a much better state could win the rest of the level by more than a frame. The search cannot see across the seam to notice.
  • Even among arrivals on the same frame, choosing by speed is a guess.

The time the guess cost us a day

Segment 2's milestone was "reach x ≥ 755 at or above height 112". The best-by-speed arrival was airborne at height 83, descending at maximum speed — a gorgeous number and a useless situation. From there Mario cannot get down onto the next ledge within the twelve pixels of travel available, so every continuation either slams into the face of the question block at column 50 (side collision, speed instantly zero, bound leaps back, deleted) or drops to the bottom floor, where climbing back up costs more than the whole rung's slack.

Segment 3 then failed at deadlines 100 through 118, each dying by layer 19 with the wavefront frozen at x ≈ 790, and exploded past twenty million records at deadline 120. Read naively, that says "crossing the lift pit is hard". It actually said "you started from a bad state."

The fix was to move the seam, not to loosen the search: milestone at x ≥ 800 instead, which sits over the block tops and forces a grounded or landing arrival. The rewritten segment solved on its first rung, arriving at full speed 47 pixels before the pit lip — and the pit segment then also solved on its first rung. Both were free.

So the rules that came out of it: a seam must be placed where the arrival state is nearly forced, not merely where a number is convenient; and the arrival gets checked against the level's geometry before it is chained, rather than being diagnosed later from a wall of dead search rungs.

And why cut at all? Two reasons, and they are the same reason twice. Memory — a 1,700-frame search has no chance of fitting anywhere. And slack — a long segment has a loose bound, loose bounds cost exponentially (chapter 07), so a long search is unaffordable even if the memory existed. Short segments have tight bounds. The craft is choosing where to cut.

Chapter 10

Memory is the wall, not speed

A frame layer of 40 million states at 96 bytes each is 3.8 gigabytes — for one frame. The engine is built around that number, not around the processor.

The first version kept the frontier in memory and died the way you would expect: killed by the kernel's out-of-memory reaper, which on one memorable occasion also took the session driving it. So the engine was rewritten as an external-memory search:

  • Each frame layer is a file on disk, one sorted list of fixed-size records.
  • Expansion threads stream parents out of the layer file and write children into a small in-memory buffer with a hard size limit. When a buffer fills, it is sorted and spilled to disk as a "run".
  • The runs are then k-way merged into the next layer file — and because the merge sees keys in sorted order, deduplication is free while it happens.
  • Any layer can be resumed from, because these runs take days and things go wrong.
  • Every search runs inside a hard memory cap. Not as a precaution — as a rule with a date on it.

Peak sizes are not modest. One of the segment searches produced 30 gigabytes of layer files. Those get deleted the moment the answer has been reconstructed and verified, because reconstruction is the only thing they exist for: the winning state names its parent, and each lower layer file is scanned to find that parent, and so on back to the start, until the sequence of button presses falls out.

This is also why the record format matters more than it sounds. Adding the enemy module to 4-2 took a state from 24 bytes to 96 — a four-fold increase in the size of every layer, every spill, every merge and every disk scan. Everything about modeling more of the game is paid for in bytes per state.

The chain so far is 415 frames from the room's entry, replayed on the real emulator 415 frames out of 415 identical, with two goomba stomps in it. Every one of those three segments came out exactly equal to the movement bound — the theoretical floor set by Mario's physics alone.

Two results that changed what we believed

  • The enemies are free. The top route walks straight into a group of three goombas on the same surface, in a corridor with 32 pixels of headroom, and the standing assumption was that this costs frames — three forced stomps, or a detour. It costs zero. A goomba stomped while you are already descending sets your vertical speed to −4 and does not touch your horizontal speed at all: taken in stride, it is not a cost. All three segments matched the enemy-free bound exactly.
  • The pit is free. The record rides a moving platform across it. The search does not: a full-power jump held for 23 frames clears the gap, passing under the vine ledge and landing on open floor, and that is the optimum.

Two results in the negative direction

Negative results are results. From the record's own state approaching the flagpole in 1-1, an exhaustive search of every input sequence shows there is no faster glitch grab — the earliest grab of any kind comes four frames later than needed, and the lowest one available is a single pixel short of triggering the glitch. That is a fifteen-year-old community belief, now with a proof artifact behind it.

And in 4-2, the record's final approach to the wrong-warp pipe is three frames loose — a real, verified saving on the real emulator. It buys nothing, because the framerule swallows it: that level's deficit merely goes from 13 to 10. It is, however, direct evidence that fifteen years of manual optimisation did not reach the floor everywhere, which is the entire premise of the project.

Chapter 12

What could still be wrong

The honest list, kept as a live document rather than a disclaimer.

  • The seams. Chapter 09. Each segment is proven; the chain is not. A level-wide proof needs either one search that spans the whole room, or a way to carry many arrival states across a seam instead of one.
  • Things the model does not contain. Items are not modeled — a mushroom, a star, a vine. That is not only about power-ups: an item also occupies an enemy slot, which is precisely why the record's vine keeps a piranha plant out of the pipe it needs to enter. Searches currently refuse to bump item blocks rather than pretend to know what happens. Swimming is modeled but not yet difference-tested. Lag frames, the random number generator and the game timer live outside the model entirely and are handled by a separate timing model.
  • Known looseness in the bounds. Documented rather than guessed. The height gate allows chains of one-frame landings on wall faces that the real game's push-out makes unrealizable, so it understates some costs. That is safe — it can only make the search slower, never wrong — but it is where the next tightening will come from.
  • Coverage, not proof, on the model itself. 877,058 differentially tested frames is a great deal of evidence that the model is the game. It is evidence, not a proof. Every refutation we write has to name which of the model's omissions could have mattered in that room, and why it did not.
  • And the thing nobody can rule out: that the frames are not in movement at all, but in a glitch — a wrong warp, a level skip, an out-of-bounds table read. That is a separate track of the project, and it is not what this page is about.

A guaranteed-not-too-large number of frames still needed from a state. If frames spent plus the bound exceeds the deadline, the state is deleted.
Admissible
The property that a bound never overstates. Lose it and the search deletes the right answer and reports a false proof.
Relaxation
An easier fantasy version of the game used to compute a bound. Impossible in the fantasy implies impossible in reality.
Deadline / rung / ladder
The frame budget a run tests. The ladder tries the tightest budget first and loosens; tight rungs are cheap, loose rungs are unaffordable.
Proof-grade
Deadline set equal to the bound: nothing on a shorter path can be pruned, so the first goal layer is the optimum, established by that single run.
Segment / seam
A short milestone-to-milestone search, and the join between two of them where one arrival state is chosen out of millions.
Differential test
Same inputs into the model and the real emulator; compare every field on every frame. How the model earns its trust.
Wall walk
A quirk of the game's side-collision order that lets Mario keep moving right while inside solid blocks at floor level. The record uses it; it costs 31 frames to get in.

Every number on this page comes from a script in the project and a log in runs/. Nothing here is folklore.
