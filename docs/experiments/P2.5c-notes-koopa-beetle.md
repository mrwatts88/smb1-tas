# P2.5c notes — green koopa troopa ($00) and buzzy beetle ($02) on the ground (4-2 rules)

Decoded from `data/disasm/smbdis.asm` (line numbers below refer to that file). Baseline: the goomba rules in
`docs/experiments/P2.5a-room1-enemies.md` §Rules, implemented in `tools/room1_enemy_sim.py`. Only what differs
from or adds to the goomba model is spelled out; everything not mentioned (spawn parser, offscreen bits, masked
bits, box-to-screen clipping, the collision core, the scroll law, interval-timer ticks) is unchanged.

Conditions assumed throughout: `PrimaryHardMode = 0`, `SecondaryHardMode = 0`, `AreaType = 2` (underground,
non-zero: the "water" special cases at 11345/11556 do not fire), no star.

Symbols: `GreenKoopa = $00` (596), `BuzzyBeetle = $02` (597), `Goomba = $06` (600). RAM: `Enemy_Y_Speed = $A0`
(311), `Enemy_Y_MoveForce = $0434` (362), `Enemy_YMF_Dummy = $0417` (357), `Enemy_CollisionBits = $0491` (367),
`Enemy_BoundBoxCtrl = $049A` (371), `StompTimer = $0791` (94), `EnemyIntervalTimer = $0796` (97),
`StompChainCounter = $0484` (183), `ShellChainCounter = $0125` (175).

## 0. Enemy_State bit layout (used everywhere below)

| bits | meaning (for $00/$02) | set by |
|---|---|---|
| d2-d0 = 0 | normal, walking | init 8013; landing 12560-12561; revive 9341 |
| d2-d0 = 1 | falling (no block under) | `EnemyBGCStateData[0]` 12586 |
| d2-d0 = 2 | bumped from below ("stunned", flipped, airborne) | `SetStun` 12466-12470 |
| d2-d0 = 3 | stunned and landed (upside-down shell, timer $10) | 12529-12530 |
| d2-d0 = 4 | stomped shell, resting (timer $10, revives) | `HandleStompedShellE` 11499-11501 |
| d5 ($20) | defeated by shell/star/block: falls off the screen, no collisions | `ShellOrBlockDefeat` 11180-11183 |
| d6 ($40) | moving shell that has walked off a ledge (falling) | `Chk2MSBSt` 12582-12584 |
| d7 ($80) | moving (kicked) shell | `HandlePECollisions` 11359-11361 |

So a resting shell is state `$04`, a kicked shell `$84`, a kicked shell in the air `$C4`, a shell-killed koopa `$22`
(or `$24`, `$2x`: `ShellOrBlockDefeat` keeps the low 5 bits, 11181-11183).

## 1. Init

- `InitEnemyObject` 8012-8016: `Enemy_State = 0`, then `CheckpointEnemyID` 8055-8066: for ID < $15 adds 8 to
  `Enemy_Y_Position` (8060-8062; the `adc` runs with carry clear from the `cmp #$15`), sets
  `EnemyOffscrBitsMasked = 1` (8063-8064), then the jump table at 8069-8133. **$00, $01, $02 all dispatch to
  `InitNormalEnemy`** (8071-8073); `$03` = `InitRedKoopa` (8074); `$06` = `InitGoomba` (8077). Group enemies
  ($3B-$3E, `HandleGroupEnemies` 8755-8812) spawn ID $00 (8756-8757) and call the same `CheckpointEnemyID`
  per member (8807) — so a group koopa is initialised exactly like a single one.
- `InitNormalEnemy` 8166-8173: `Y = PrimaryHardMode ? 1 : 0` → `Enemy_X_Speed = NormalXSpdData[Y]` =
  **$F8** (8163-8164: `$f8, $f4`; hard mode would give $F4 = -0.75 px/f) → `jmp TallBBox`.
- `TallBBox` 8223: **`Enemy_BoundBoxCtrl = $03`** (vs `InitGoomba` 8138-8140 → `SmallBBox` 8209-8210 → `$09`).
  `SetBBox` 8224-8226: **`Enemy_MovingDir = 2` (left)**. `InitVStf` 8227-8230: **`Enemy_Y_Speed = 0`,
  `Enemy_Y_MoveForce = 0`** (the goomba path reaches the same `SetBBox`/`InitVStf`, so this is not a difference).
- Bounding boxes, `BoundBoxCtrlData` 12766-12778 (4 bytes per ctrl: left, top, right, bottom, added to the
  screen-relative x/y by `BoundingBoxCore` 12853-12889):
  - ctrl 3 (12770): `$02, $09, $0e, $15` → **x+2 … x+14, y+9 … y+21** (13 × 13 px) — koopa, beetle, red koopa.
  - ctrl 9 (12776): `$03, $0e, $0d, $14` → x+3 … x+13, y+14 … y+20 (11 × 7 px) — goomba (P2.5a).
  - The box ctrl is never rewritten for $00/$02 after init (the only `sta Enemy_BoundBoxCtrl` sites are the
    init routines 8224/8238/8617/8874/8939/8977, bullet bill 6803, power-up 7142, platform 10304), so a shell
    (state 4/$84) keeps the tall 13 × 13 box.
- Not initialised (stale slot memory, exactly as for the goomba): `Enemy_X_MoveForce` (sub-pixel phase),
  `Enemy_CollisionBits`, `Enemy_YMF_Dummy` (vertical sub-pixel accumulator, see §3.6). `EraseEnemyObject`
  9173-9182 clears only `Enemy_Flag`, `Enemy_ID`, `Enemy_State`, `FloateyNum_Control`, `EnemyIntervalTimer`,
  `ShellChainCounter`, `Enemy_SprAttrib`, `EnemyFrameTimer`.
- Set by the spawner, not the init: `Enemy_Y_HighPos = 1` (`CheckRightExtBounds` 7964-7965; group 8804-8805),
  `Enemy_PageLoc`/`Enemy_X_Position`/`Enemy_Y_Position` (7942-7970, 8791-8803), `Enemy_Flag = 1`.

## 2. Horizontal movement — `MoveNormalEnemy` 9293-9335

Dispatch: `RunNormalEnemies` 9067-9080 → `EnemyMovementSubs` 9082-9105: IDs $00, $01, $02 (and $06) →
`MoveNormalEnemy` (9086-9088, 9092). Skipped entirely while `TimerControl ≠ 0` (9076-9077).

Decision tree (9294-9322), in order:
```
Y = 0
if state & $40:             goto FallE                     # falling moving shell
elif state & $80:           goto SteadM                    # moving shell on the ground
elif state & $20:           goto MoveDefeatedEnemy (9356)  # killed: gravity + raw horizontal speed
elif (state & 7) == 0:      goto SteadM                    # walking
elif (state & 7) == 5:      goto FallE                     # spiny egg (n/a)
elif (state & 7) >= 3:      goto ReviveStunned (9338)      # states 3, 4: NO horizontal movement
else (state&7 in {1,2}):    FallE
FallE:  MoveD_EnemyVertically (gravity, §3.6); Y = 0
        if state == 2:      MoveEnemyHorizontally (raw speed, no adder)         # 9313-9315, 9322
        elif state & $40 == 0: goto SteadM                                      # state 1: full speed
        elif ID == PowerUpObject: goto SteadM
        else:               SlowM: Y = 1                                         # $C4 shell: half speed
SteadM (9325-9335):
        saved = Enemy_X_Speed
        if saved < 0 (bit 7): Y += 2
        Enemy_X_Speed = saved + XSpeedAdderData[Y]   (8-bit, carry ignored)
        MoveEnemyHorizontally
        Enemy_X_Speed = saved                        # the adder is temporary
```
- `XSpeedAdderData` 9207-9208: `$00, $e8, $00, $18`. Index meaning: bit 0 = "slowed" (d6 shell in the air),
  bit 1 = "speed is negative". So a walking enemy (Y = 0 or 2) moves at its stored speed; an airborne kicked
  shell moves at `$30 + $E8 = $18` (right) or `$D0 + $18 = $E8` (left) = ±1.5 px/f instead of ±3.
- `MoveEnemyHorizontally` 7530-7534 → `MoveObjectHorizontally` 7541-7577, for speed `s` and force `f`
  (`Enemy_X_MoveForce`):
  ```
  lo  = (s << 4) & $FF                # 7542-7547
  hi  = s >> 4; if hi >= 8: hi |= $F0 # 7548-7555  (sign-extend the high nybble)
  pg  = $FF if hi & $80 else $00      # 7557-7561
  f   = f + lo; c = carry             # 7562-7565
  x   = x + hi + c; c2 = carry        # 7570-7572
  page = page + pg + c2               # 7573-7575
  return (hi + c) in A                # 7576-7578 (unused by callers here)
  ```
  Per speed (px/frame; "force += lo" runs every frame, the carry is the sub-pixel):
  | speed | lo | hi | x delta |
  |---|---|---|---|
  | $F8 (walking left) | $80 | $FF | −1 + carry → **−0.5/f** (phase = bit 7 of force) |
  | $08 (walking right, after revive) | $80 | $00 | 0 + carry → +0.5/f |
  | $F0 / $10 (shell-killed, §4.5) | $00 | $FF / $01 | −1 / +1 exactly |
  | $D0 / $30 (kicked shell) | $00 | $FD / $03 | **−3 / +3 exactly**, force untouched |
  | $E8 / $18 (kicked shell in the air) | $80 | $FE / $01 | −2 + c / +1 + c → ∓1.5/f |
  Carry semantics: `f + lo` is 8-bit; the carry feeds the x add; the page gets `pg + carry-of-x`. With `lo = 0`
  the force is not touched at all, so a shell keeps the sub-pixel phase it had when kicked.
- States 3 and 4 (`ReviveStunned` 9338-9354): if `EnemyIntervalTimer ≠ 0` → `ChkKillGoomba` 9360-9367 (erases
  only a goomba, and only when the timer is exactly $0E; a koopa/beetle does nothing) — **no movement at all**.
  When the timer is 0: `state = 0`; `Enemy_MovingDir = 1 + (FrameCounter & 1)` (9342-9346: Y = fc&1, `iny`);
  `Enemy_X_Speed = RevivedXSpeed[fc & 1]` = `$08` (dir 1, right) or `$F8` (dir 2, left) (9210-9211, +2 in hard
  mode). The revived enemy moves in the same frame? No: `ReviveStunned` returns without calling the move, so
  the first step is on the next frame. Y position is not touched (it is already at the standing height).
- `MoveDefeatedEnemy` 9356-9358 (d5 set): gravity (§3.6) then `MoveEnemyHorizontally` with the raw speed.

## 3. Background collision — `EnemyToBGCollisionDet` 12401-12431

Order in the frame (`RunNormalEnemies` 9067-9080): sprite attrib → offscreen bits → relative position →
**graphics handler** (which can erase, §5) → bounding box → **`EnemyToBGCollisionDet`** → `EnemiesCollision` →
`PlayerEnemyCollision` → movement → `OffscreenBoundsCheck`. So, as for the goomba, **the BG check sees the
position from the end of the previous frame, before this frame's move**.

### 3.1 Entry gates
- 12402-12404: d5 set (defeated) → exit. (Comment says d6; the mask is `%00100000` = d5.)
- `SubtEnemyYPos` 12654-12659: `A = y + $3E` (8-bit, clc), `cmp #$44` → carry clear → exit (12405-12406).
  So BG collision runs only for **6 ≤ y ≤ $C1 (193)**; y ≥ $C2 wraps the add and exits. (A koopa at the 4-2
  floor height y = $B8 is inside the range; an enemy that has fallen below y = $C1 stops colliding.)
- 12407-12426: spiny/paratroopa/hammer-bro special cases; `cpy #$07; bcs ExEBGChk` (12424-12425): IDs ≥ 7
  (other than spiny/power-up) skip BG collision. $00 and $02 pass to `YesIn` 12427.

### 3.2 Block-buffer sample points (`BlockBufferChk_Enemy` 12998-13005 → `BBChk_E` 13022-13026 →
`BlockBufferCollision` 13053-13090)
- Adder tables `BlockBuffer_X_Adder` 13030-13034 / `BlockBuffer_Y_Adder` 13036-13040, index Y:
  - **Y = $15** (`ChkUnderEnemy` 12707-12710, A = 0): X adder $08, Y adder $18 → sample **(x+8, y+24)**.
  - **Y = $16** (`DoEnemySideCheck`, left): X adder $00, Y adder $14 → **(x+0, y+20)**.
  - **Y = $17** (right): X adder $10, Y adder $14 → **(x+16, y+20)**.
- Address: `$05 = (x + xadd) & $FF` with carry into the page; column = `(page+carry) & 1` as bit 4 |
  `$05 >> 4` (13060-13068); `GetBlockBufferAddr` 4328-4341 picks the page half by that bit and adds the
  column. Row: `Y = ((y + yadd) & $F0) - $20` (13071-13077), i.e. block-buffer row = `(y + yadd − 32) >> 4`
  (rows 0..12 cover screen y 32..239). The metatile is `($06),Y` (13079-13080); `Enemy_Y_HighPos` is ignored.
- Return (13081-13090): A = metatile, Z set iff metatile = 0; **`$04` = low nybble of y** when called with
  A = 0 (`ChkUnderEnemy`), low nybble of x when called with A = 1 (side check). `$02` = the row offset.
- "Solid" for enemies (`ChkForNonSolids` 12712-12722): **any non-zero metatile except $26 (vine blank),
  $C2, $C3 (coins), $5F, $60 (hidden blocks)**. There is no attribute test, so every visible metatile —
  bricks, ground, pipes, used blocks — both supports and blocks a koopa.

### 3.3 Block underneath → `HandleEToBGCollision` 12436-12453 → `LandEnemyProperly` 12498-12510
- 12437-12438: non-solid under → treated as nothing under (→ `ChkForRedKoopa`, §3.4).
- 12439-12453: metatile $23 (a block Mario is bumping from below) → bump handling: `ChkToStunEnemies`
  12455-12465 → `SetStun` 12466-12493: `state = (state & $F0) | 2`; `y -= 2`; `Enemy_Y_Speed = $FD`
  (non-water); `Enemy_MovingDir` = away from Mario (1 if enemy x ≥ player x 16-bit, else 2, 12480-12489);
  `Enemy_X_Speed = EnemyBGCXSpdData[dir-1]` = `$10` / `$F0` (12398-12399). Not a 4-2 walking concern;
  listed for completeness.
- `LandEnemyProperly` 12499-12502: `L = $04 = y & $0F`; `(L − 8) mod 256 ≥ 5` → **not a landing** → jump to
  `ChkForRedKoopa` (§3.4). So landing processing happens only when **L ∈ {8, 9, A, B, C}**. (Standing height
  has L = 8; a fall moves ≤ 4 px/frame (speed 3 + carry, §3.6), so it first enters the ground row with L in 8..B.)
- 12503-12510: d6 set (airborne kicked shell) → `LandEnemyInitState`; d7 set (kicked shell on ground) →
  `SChkA` = `DoEnemySideCheck` directly; else → `ChkLandedEnemyState` 12512-12531:
  - state 0 (walking): → `DoEnemySideCheck` (12513-12514). Nothing else happens on the ground.
  - state 1 (falling): → `ProcEnemyDirection` 12533-12551 (since 1 ≠ 5, 1 < 3, 1 ≠ 2).
  - state 2 (stunned, airborne): `EnemyIntervalTimer = $10`, `state = 3`, `EnemyLanding` (12522-12530).
  - states 3, 4: nothing (12517-12518 `bcs ExSteChk`). A resting shell on the ground is inert in BG collision.
- `ProcEnemyDirection` 12533-12553 (koopa/beetle: not goomba, not spiny → `InvtD` 12546):
  `Y = 1`; `PlayerEnemyDiff` 12635-12642 (`enemy_x16 − player_x16`, sign from the page byte); if negative
  (enemy left of Mario) `Y = 2`. **If `Y == Enemy_MovingDir` → `ChkForBump_HammerBroJ` 12613-12629 →
  `RXSpd` (turn around)**; no bump sound because d7 is clear (12616-12618). Then `LandEnemyInitState`.
  Net effect: **a koopa/beetle that lands after a fall ends up walking toward Mario** (enemy right of
  Mario and moving right → reversed to left; enemy left of Mario and moving left → reversed to right;
  already facing Mario → unchanged). A goomba skips this (12534-12536) and keeps its direction.
- `LandEnemyInitState` 12555-12562 → `EnemyLanding` 12646-12652: `InitVStf` (Y speed and Y force = 0;
  `Enemy_YMF_Dummy` is not reset), **`y = (y & $F0) | 8`**; then `state = 0` (d7 clear) or, for a kicked
  shell, `state &= ~$40` (`NMovShellFallBit` 12564-12567).

### 3.4 Nothing underneath → `ChkForRedKoopa` 12572-12577 / `Chk2MSBSt` 12578-12586
- Not red koopa → `Chk2MSBSt`: d7 set → `state |= $40` (kicked shell starts falling, half horizontal speed);
  else `state = EnemyBGCStateData[state]` with the table 12395-12396 = **`$01, $01, $02, $02, $02, $05`**
  (index = old state, which is < 6 here): 0→1, 1→1, 2→2, 3→2, 4→2, 5→5. So a walking koopa becomes state 1
  (falling, full horizontal speed); a resting or upside-down shell whose support disappears becomes state 2
  (falls, moves horizontally at its stale stored speed, lands as state 3 with a fresh $10 timer).
- **Falls through into `DoEnemySideCheck`** (12586 is immediately followed by 12592): the wall test also
  runs on frames where the enemy is airborne, so a falling koopa still reverses at a wall.

### 3.5 `DoEnemySideCheck` 12592-12611
- 12593-12595: y < $20 → exit.
- Loop over Y = $16 (left, `$eb = 2`) then Y = $17 (right, `$eb = 1`); only the point whose code equals
  `Enemy_MovingDir` is sampled (12599-12601). Left-moving: **(x+0, y+20)**; right-moving: **(x+16, y+20)**.
  With y = $B8 that is y+20 = $CC → row (0xCC − 0x20) >> 4 = 10, the row just above the floor.
- Solid there (non-zero and not in `ChkForNonSolids`) → `ChkForBump_HammerBroJ` → `InvEnemyDir` 12629-12630
  → `RXSpd` 11696-11704: **`Enemy_X_Speed = −speed` (two's complement, 8-bit), `Enemy_MovingDir ^= 3`**.
  Position and force are untouched. For a kicked shell (d7) the same path also queues `Sfx_Bump`
  (12616-12620). Only one side is tested, so the enemy can be overlapping a block on its trailing side.
- Summary, koopa walking left at y = $B8, floor = block-buffer row 11, ledge edge at block column c
  (block x = 16c): each frame, before the move, the game samples (x+8, y+24) → row 11, column (x+8)>>4.
  **It steps off when x+8 < 16c, i.e. x ≤ 16c − 9** (x moves in whole pixels, 1 px every other frame): on
  that frame `state` becomes 1, the side point (x, y+20) is also checked, then the move subtracts 0 or 1 px and
  `MoveD_EnemyVertically` starts gravity (first frame: y unchanged, force $3D). **It turns at a wall when the
  block at (x, y+20) is solid, i.e. when x < 16(c'+1) for a wall occupying column c' at row 10** — the turn
  happens on the first frame with x ≤ 16c' + 15, still before the move; the speed becomes $08 and the next
  move adds 0 or 1 px (force phase). A one-block step (a solid block at row 10, resting on the floor) is
  exactly what the side point sees; the floor row itself (row 11) is never sampled by the side check. Note both tests happen in the same `EnemyToBGCollisionDet` call: ground first, then side.

### 3.6 Falling arithmetic — `MoveD_EnemyVertically` 7599-7607 → `SetHiMax` 7644-7649 → `ImposeGravitySprObj`
7666-7669 → `ImposeGravity` 7704-7759
- Parameters: downward force `$00 = $3D` (7600; `$20` only for state 5), max speed `$02 = 3` (7644),
  upward amount not used (A = 0 pushed → 7736-7737 leave).
- Per frame, all 8-bit:
  ```
  t = Enemy_YMF_Dummy + Enemy_Y_MoveForce; c1 = carry; Enemy_YMF_Dummy = t   # 7706-7709
  hi = $FF if Enemy_Y_Speed < 0 else $00                                     # 7710-7714
  y = y + Enemy_Y_Speed + c1; c2 = carry                                      # 7715-7716
  Enemy_Y_HighPos = Enemy_Y_HighPos + hi + c2                                 # 7717-7719
  Enemy_Y_MoveForce = Enemy_Y_MoveForce + $3D; c3 = carry                     # 7720-7723
  Enemy_Y_Speed = Enemy_Y_Speed + c3                                          # 7724-7726
  if (Enemy_Y_Speed - 3) is not negative (i.e. speed >= 3 for small values)   # 7727-7728
      and Enemy_Y_MoveForce >= $80:  Enemy_Y_Speed = 3; Enemy_Y_MoveForce = 0 # 7729-7735
  ```
  The "dummy" accumulator turns the force into real sub-pixel motion: y advances by `speed` plus the carry of
  `dummy + force`. `InitVStf`/`EnemyLanding` zero speed and force but **not the dummy**, so the sub-pixel
  phase of a fall depends on stale slot memory (like `Enemy_X_MoveForce`). The clamp fires whenever
  speed ≥ 3 and force ≥ $80 (7727-7731), not only on a carry, so once the speed reaches 3 the force cycles
  0 → $3D → $7A → ($B7, clamped to 0) every three frames and the speed stays at 3; the dummy receives
  $3D + $7A + 0 per cycle, i.e. the terminal motion is 3 px/f plus 183/768 ≈ 0.24 px/f (pattern Δ3, Δ3, Δ4 …
  with its phase set by the stale dummy). Trace from rest, dummy = 0 (speed, force after the frame, Δy that
  frame = old speed + carry(dummy + old force); `*` = clamp fired; checked numerically):
  f1 (0,$3D,0) f2 (0,$7A,0) f3 (0,$B7,0) f4 (0,$F4,1) f5 (1,$31,1) f6 (1,$6E,1) f7 (1,$AB,2) f8 (1,$E8,1)
  f9 (2,$25,2) f10 (2,$62,2) f11 (2,$9F,3) f12 (2,$DC,2) f13 (3,$19,3) f14 (3,$56,3) f15 (3,$00*,4)
  f16 (3,$3D,3) f17 (3,$7A,3) f18 (3,$00*,3) f19 (3,$3D,3) f20 (3,$7A,3) f21 (3,$00*,4) … (57 px after 25
  frames). The first pixel of descent comes on the 4th frame of the fall. A simulator must carry
  `Enemy_YMF_Dummy` per slot.
- Drop timing. The fall starts in frame 1 (BG check finds nothing under → state 1; the move then applies f1).
  The probe (x+8, y+24) re-enters a solid floor k blocks lower once y ≥ y_stand + 16k; the BG check of the
  *next* frame lands it (y low nybble is then in 8..B, within the 8..C window), snapping y to
  `(y & $F0) | 8` = y_stand + 16k, zeroing speed/force, state 0, direction per §3.3, and that same frame's move
  is already horizontal-only. Frames spent in state 1 (y ≥ threshold reached after frame n; landing in the BG
  check of frame n+1), over all 256 stale dummy values: **1 block: n = 12 or 13; 2 blocks: n = 17 or 18;
  3 blocks: n = 22 or 23** (dummy = 0 gives 13 / 18 / 23). Horizontal motion continues at full speed
  throughout (state 1 → `SteadM`, §2), so a koopa walking at −0.5 px/f drifts 6–7 px during a one-block drop.

## 4. Player contact — `PlayerEnemyCollision` 11293-11314

- Gates (unchanged from goomba): even `FrameCounter` only (11294-11296); `CheckPlayerVertical` 11867-11876
  (`Player_OffscreenBits < $F0`, `Player_Y_HighPos = 1`, `Player_Y_Position < $D0`); `EnemyOffscrBitsMasked
  = 0`; `GameEngineSubroutine = 8`; enemy d5 clear (11304-11306 — states 1, 2, 3, 4, $84 all still collide).
  No overlap → `Enemy_CollisionBits &= ~1` (11311-11313). Overlap → `CheckForPUpCollision` 11316-11323
  → `EColl`: star active → `ShellOrBlockDefeat` (§4.5), else `HandlePECollisions` 11328-11374.
- `HandlePECollisions`: if `Enemy_CollisionBits & 1` or masked → exit (11328-11331), else set d0 (11332-11334).
  For $00/$02: not spiny/piranha/podoboo/cannon-bill, < $15, `AreaType ≠ 0`, then:
  - **d7 set (kicked shell) → `ChkForPlayerInjury`** (11347-11349).
  - **`(state & 7) < 2` (walking or falling) → `ChkForPlayerInjury`** (11350-11353).
  - **`(state & 7) ≥ 2` (states 2, 3, 4) → kick** (11357-11373; the goomba early-out 11354-11356 does not
    apply): `Sfx_EnemySmack`; `state |= $80`; `EnemyFacePlayer` 11524-11530 sets `Enemy_MovingDir` = 1 if
    enemy x16 ≥ player x16 else 2 (shell goes *away* from Mario); `Enemy_X_Speed = KickedShellXSpdData[dir-1]`
    = **`$30` (right) / `$D0` (left)** (11287-11288) = ±3 px/f exactly; points from `KickedShellPtsData`
    11325 / `StompChainCounter + 3`. Note a kick needs only overlap: Mario's y speed is not consulted, so
    landing on a resting shell kicks it. State 3 (upside-down) becomes `$83`, a moving shell too.
- `ChkForPlayerInjury` 11376-11399:
  ```
  if Player_Y_Speed > 0 (positive, non-zero):       EnemyStomped            # 11377-11379
  if Enemy_ID < Bloober ($07):                      skip the y test         # 11380-11382 ($00/$02 skip it)
  if StompTimer != 0:                               EnemyStomped            # 11388-11389
  if InjuryTimer != 0:                              exit                    # 11390-11391
  if Player_Rel_XPos < Enemy_Rel_XPos:  (Mario left of enemy)               # 11392-11394
        if Enemy_MovingDir != 1 (moving left, toward Mario): InjurePlayer    # 11396-11398
        else: EnemyTurnAround, then InjurePlayer                            # 11399, 11520-11521
  else: (Mario at/right of enemy)                                           # 11515-11521
        if Enemy_MovingDir == 1 (moving right, toward Mario): InjurePlayer
        else: EnemyTurnAround, then InjurePlayer
  ```
  So the stomp test is purely **`Player_Y_Speed > 0` (signed) at the moment of overlap, or a stomp already
  registered this frame** — there is no relative-height test for IDs < 7, same as the goomba. Side contact
  with `Player_Y_Speed ≤ 0` injures Mario (`InjurePlayer` 11401-11403 → `ForceInjury` 11405-11421: big →
  small, `InjuryTimer = 8`, `GameEngineSubroutine = $0A`, `Player_State = 1`, `TimerControl = $FF`,
  `ScrollAmount = 0`; small → `KillPlayer` 11427-11434) and, if the enemy was walking away from Mario,
  reverses it first (`EnemyTurnAround` 11682-11704 applies to IDs < 7 and to a kicked shell alike).
- `StompTimer` ($0791) lies in the frame-timer block $0780-$0794 that the NMI decrements every frame
  (`DecTimers` 789-799, `ldx #$14`), so a stomp sets it to 1 for the rest of the current frame (enabling
  chained stomps on later slots in the same frame even though `Player_Y_Speed` is now negative) and it is 0
  again at the start of the next frame. Nothing else writes it (only 11388, 11505, 11507 reference it).
- `EnemyStomped` 11439-11463 for $00/$02: not spiny → `Sfx_EnemyStomp`; the ID chain (11445-11463) matches
  none of cheep/bullet/podoboo/hammer-bro/lakitu/bloober → `ChkForDemoteKoopa` 11481-11483: ID < 9 →
  **`HandleStompedShellE` 11499-11511**:
  - `Enemy_State = 4` (a kicked shell `$84` is stopped the same way — d7 cleared);
  - `StompChainCounter += 1`; points = `StompChainCounter + StompTimer`; `StompTimer += 1`;
  - **`EnemyIntervalTimer = RevivalRateData[PrimaryHardMode] = $10`** (11496-11497: `$10, $0b`);
  - **`Player_Y_Speed = $FC` (−4)** (`SBnce` 11511-11513).
  - **Not changed**: `Enemy_X_Speed`, `Enemy_MovingDir`, `Enemy_Y_Position`, `Enemy_Y_Speed`, the box ctrl.
    (Contrast `EnemyStompedPts` 11465-11479 used by cheeps/bullets/hammer bros/lakitu/bloober: d5 set, speeds
    zeroed, bounce `$FD`. Koopas/beetles/goombas never take that path.)
  - Identical for the goomba; the difference is afterwards: goomba erased at timer $0E (`ChkKillGoomba`),
    koopa/beetle revive at timer 0 (§2). Timer $10 ticks on `IntervalTimerControl` wraps (every 21 frames),
    so a resting shell revives 16 ticks later: between 15×21+1 and 16×21 frames after the stomp.
- Mario's bounce is the only player-side effect; Mario's position is not moved.
