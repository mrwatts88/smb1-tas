### Two derivation traps (both cost time here — do not repeat)
- The x subpixel is **`$0400`**. `$0705` is the *speed* fraction (`XFRAC`), not position.
- The model's `y_pos` **low byte is not** the core's `$0433`. Compare via `model_difftest`'s field
  set (XP/XSUB/XSPD/XFRAC/YP/YSPD/YFRAC); never hand-assemble a 24.8 word from RAM.
- `v_force` is an **encoded enum** (`options.rs:362`), so the core's raw `$0709` = 0 is not a legal
  model value. `V_FORCE_AREA_INIT` is right for a control frame — `W84Room3` shows the same pattern.
- Sanity method that caught all of the above: run the identical comparison against **`W84Room3`**,
  which is known-good. If it "fails" too, the comparison is wrong, not the new case.

### RESOLVED: `$0e` is a jumping Green Paratroopa, not a lift

`E_CastleArea6` places **id `$0e`** objects at page 8 cols 11/13 and page 9 cols 11/13 (x 2224, 2256,
2480, 2512); two of them (x 2224, 2256) are inside room 2's span. MrWint's comment calls them "the

So the port needs **one new class** beyond what already exists: a leftward walker with a periodic
jump arc. Deterministic (no RNG), so a phase counter should cover it — confirm the arc is
frame-indexed rather than player-coupled during the difftest.

### Remaining open question before coding
Whether the paratroopa's jump phase is purely frame-indexed on this lag-free route (cheap: one phase
counter in the slot) or coupled to the player (expensive). The difftest over the WR's 267 frames
answers it directly — that is the first thing to check once the class is stubbed in.

# Part 2 — the port, and what it took (session 17)

## 5. What shipped

The engine stayed **one** module (`w42enemies`), now parameterised twice over: on the **area**
(`Frame::edata` / `Frame::pipes`, session 16) and on the **terrain** (`Slots::step::<B>`,
`block_at::<B>` — `BB42` for 4-2, `BB84` for 8-4). Everything else is new rules, not new code paths.

**The `$0e` jumping Green Paratroopa (`CLASS_PARA`).** Derived from the disassembly, not from the trace:

| piece | asm | rule |
|---|---|---|
| init | `InitJumpGPTroopa` (8868) | dir 2, x speed `$f8`, bbox ctrl 3 (the tall box the model already uses for non-goombas). It ends at `TallBBox2`/`SetBBox2`, **not** `SetBBox`, so **no `InitVStf`**: y speed, y move force and the YMF dummy start as the slot's stale memory. |
| movement | `MoveJumpingEnemy` (9371) | `MoveJ_EnemyVertically` (downward force **`$1c`**, max speed 3) + a full-speed `MoveEnemyHorizontally`. Dispatched by **ID**, so it applies in every `Enemy_State` — including defeated. |
| BG collision | `EnemyJump` (12661) | nothing like the walkers' `HandleEToBGCollision`: if `(y + $3e) & $ff >= $44` and `(y_speed + 2) >= 3` (i.e. falling) and `ChkUnderEnemy` finds a solid non-`$26/$c2/$c3/$5f/$60` metatile, then `EnemyLanding` + y speed `$fd` — the hop restarts. Then the ordinary side check. |
| stomped | `ChkForDemoteKoopa` (11481) | id `&= 1` -> **Green Koopa**, state 0, `InitVStf`, `EnemyFacePlayer` + `DemotedKoopaXSpdData` (`$08`/`$f8`). No StompChainCounter/StompTimer increment. Player bounce `$fc`. |

Class 8 does not fit the 3-bit class field, so it is packed as **low bits 000 with byte 0's bit 7 set** —
a combination the "plant travelling up" flag (class 4) can never produce. Every 4-2 record keeps its exact
old bytes.

**A stomp rule 4-2 and 1-1 never needed.** `ChkForPlayerInjury` (11439) sends a player with
`Player_Y_Speed <= 0` to `ChkInj`, and there an object with **id >= `$07`** is *still* stomped when
`Player_Y + 12 < Enemy_Y`. Every 4-2 / 1-1 enemy has id < `$07`, so the model only had the falling case.
The WR's room-2 paratroopa stomp happens while Mario is **rising at y speed -4** (dump row 16083) and is
unreachable without this branch.

**Plant stale memory.** `PiranhaPlantDownYPos` / `PiranhaPlantUpYPos` *are* the slot's `$0434` / `$0417`.
The old packing wrote 0 into byte 9 for a plant, so an erased plant handed its successor `YMF_Dummy = 0`
instead of `dn - 24`. In 4-2 nothing ever noticed; in 8-4 room 2 a paratroopa takes over an erased plant's
slot and its gravity accumulator starts from that byte, which shifts every carry frame afterwards.

## 8. The case had to grow, and the shared key layout had a latent bug

`W84Room2` was `NoScrollPos` with no block states — fine for an enemy-free search, impossible with enemies:
the loader, the offscreen bits and the plant spawns all read `screen_left16`, and the timer phases and the
parser column come from `State.blocks`. So the case is now `WithScrollPos` + `WithBlockBounceTimer` +
`W84Room2Blocks`, and its key grew 11 -> 20 bytes. Phases read from the WR dump at the case's own start
record (fceux RAM index 15917): FrameCounter 120, IntervalTimerControl 1, GameTimerCtrlTimer 24,
AreaParserTaskNum 0 with CurrentPageLoc 8 / CurrentColumnPos 8 -> **PARSER_COL0 = 136**, VRAM_Buffer1
non-empty, AddrCtrl 0. The span holds exactly **one** bumpable metatile, the hidden coin block `$5f` at
(150, 7), so `CELLS` is a single entry.

That start column exposed a latent bug in the *shared* compressed state: `BlockStateData::parser_col` is a
`u8` but only **7 bits** were packed, so 136 round-tripped to **8** and the case panicked on the
compress/decompress assert. Both 4-2 (24) and 1-1 (24) were under 128, so nothing had ever noticed. The
top bit now goes into one of the two spare bits at the **end** of the 56-bit block-state field, which keeps
every existing 4-2 / 1-1 record byte-identical and leaves `BITS` at 56.

Room 2 also starts with a **non-empty** ext — three plants already spawned at (115,9) / (122,8) / (132,9),
two Buzzy Beetles that have walked in from page 8, stale x 2128 in slot 5, and the loader at
`EnemyDataOffset` 18 / `EnemyObjectPageLoc` 8 — so the `ext0` plumbing now carries a full `Ext` instead of
a `u16` (`w84_room2_ext0()`; 4-2 and 1-1 pass the old `0x100 | aptn` preset through `w42ext0`).

## 9. F137 — the x-only bound cannot carry the tail

The WR's last 22 frames are a two-stage climb, and it is stranger than it looks: Mario runs into the clip
pipe's **left face**, and because his right foot point is inside col 152 at row 6 he *lands on the pipe's
body* and stands wedged at **Y 96**; from there he jumps to the cap (Y 64) and walks right — slowly, from
a standstill — the last 13 px to x 2436.

The case bound was the plain x table to x 2436. The frontier reaches x 2436 **at floor level** about 15
frames before the goal, and from there `h = 0` for every state: no signal for the climb at all. Measured
at the WR's own deadline 267, a bucketed beam finds **no goal**:

| beam | states/layer | wall | result |
|---|---|---|---|
| `--beam 50 --beam-buckets off,y,spd,sub` | ~10-17k | 70 s | no goal; frontier at floor level, max x 2459 |
| `--beam 2000 --beam-max 400000` | ~300k | 395 s | no goal; max x 2471 |

The fix is a y-coupled bound over the goal's own **necessary** condition — the entry can only fire standing
on the cap, so every goal state has `x >= 2436 && Player_Y <= 64`. `YGate` over
`surfaces_from_blocks::<BB84>(304)` with `y_max = 64`, joined with the x table.

**Trap worth remembering:** `YGate::steps_xy` is a "steps until it holds in the FUTURE" bound — its scan
starts at `k = 1`, so it never returns 0 and over-counts by 1 on a state that *already* satisfies the
condition. The goal state does, so using it raw prunes the WR's own goal (`--check-path` reported
`h Some(1)` at the GOAL step and 1 bound violation). States already satisfying the condition are given
`h = 0` explicitly.

Audits after the fix: the WR line is clean (0 bound violations over 267 steps, `h = 0` at the goal), and
`tools/ygate_audit.py --case W84Room2 --gx 2436 --gy 64 --enemies 0 --mutate data/wr/wr_inputs.bin 267
0.015 --n 300` gives **1335 admissibility checks, 0 violations, min slack 0** and no `Y_NEVER` on any
goal path. (The unmutated random audit is useless here: 0 of 200 random trajectories ever reach the
climb.)

## 10. Where the search stands

With the y-coupled bound the beam behaves completely differently — the bound now kills the floor-level
states, and at width 200 the frontier goes **extinct at layer 264**, 7 px short (max x 2429). That is the
beam being too narrow near the end, not a verdict: the WR path itself survives every bound test. A wider
control is running.

**Reading rule, pre-registered:** the d266 run means nothing until the **d267 control finds a goal**. A
beam that cannot reproduce the WR's own 267 cannot be trusted to say anything about 266.

Next lever if width alone does not do it: the bucket key has no enemy axis (H40 asks for beetle x/state,
plant phase, paratroopa phase, slot occupancy), so two states with the same physics but different enemy
configurations compete for the same slots.

## 11. F138 — the beam does not fail at the climb; it fails at layer 40

`bfscx --check-path N` prints, for every layer, whether the reference path is still in the frontier. Run on

§10 was aimed at the wrong end of the room.

The cause is structural, and the prefix probes measure it: the WR's own state is **14-15 frames above the
bound at every root**, constantly.

| root = the WR's step | deadline (one better than the WR) | root bound h | slack |
|---|---|---|---|
| 180 | 86 | 72 | 14 |
| 200 | 66 | 52 | 14 |
| 220 | 46 | 32 | 14 |
| 240 | 26 | 13 | 13 |

That slack is the tail the bound cannot see (Mario must LAND before he can jump onto the cap; the gate
prices an immediate jump). An h-first beam therefore prefers, at every layer, the family that is *ahead* of
the WR on x — and the WR's family is systematically behind by construction. Adding an **absolute-x** bucket
axis (new `--beam-buckets x`) does not rescue it: the beam still drops the reference at layer 40, because
inside a 16 px x-band h-first still keeps the states at the band's right edge.

Conclusion: **for this room a beam is the wrong tool**, and no amount of width or bucket diversity fixes a
bound that is loose by 14 frames over the whole span. Recorded rather than "tuned around".

## 13. Where the 14 frames of slack actually are — the profile that specifies the next unit

`bfscx --check-path 267` prints `h` at every step of the reference path, so the bound's optimism can be
read off directly against the true remaining cost (`runs/P2.2f/wr_hprofile.txt`):

| WR step | x | Y | state | h | true | **slack** |
|---|---|---|---|---|---|---|
| 225 | 2368 | 140 | JUMPING | 27 | 42 | **15** |
| 235 | 2393 | 109 | JUMPING | 17 | 32 | **15** |
| 240 | 2405 | 100 | JUMPING | 13 | 27 | **14** |
| 245 | 2417 | 96 | JUMPING | 8 | 22 | **14** |
| **246** | **2419** | **96** | **STANDING** | **17** | **21** | **4** |
| 247 | 2418 | 91 | JUMPING | 18 | 20 | 2 |
| 250 | 2418 | 77 | JUMPING | 16 | 17 | 1 |
| 257 | 2423 | 64 | STANDING | 9 | 10 | 1 |
| 264 | 2432 | 64 | STANDING | 3 | 3 | 0 |

The whole error is in the **airborne approach**, and it collapses the instant Mario lands: at step 245 the
bound says 8 (truth 22); one frame later, standing on the wedge, it says 17 (truth 21). The bound is
essentially **tight from step 247 onward** — the climb itself is priced correctly.

So the optimism is one specific thing. While airborne the gate reaches `Y <= 64` through its Y-96 surface
term with `t_surf[Y96] = 6` — a 32 px climb at a *running* jump's arc (5 px on the first frames). But the
wedge at Y 96 exists **only because Mario hit the pipe's left wall**, so he is standing there at
`x_spd ~ 0`, and a standstill jump is the weakest arc the game has: the WR's own climb takes **10 frames**
(246 -> 256), not 6. Add the 10 frames of walking the cap from that same standstill and 8 becomes 22.

**Next unit, precisely stated:** condition the Y-96 -> Y-64 term on the x speed actually available on that
surface. The wedge's speed is not a guess — it is forced by the wall push-back that creates the wedge — so
a room-2 end-game term of the form "from the Y-96 wedge: >= 10 frames to the cap, then >= 10 frames to walk
to x 2436 from a standstill" is sound and closes essentially all 14 frames. Build it as a small exact table
over the last ~30 frames indexed by (Y, y_spd, v_force, x, x_spd), by backward search on the real model;
the prefix-240 rung shows that region is exhaustively searchable in ~10 s, so the table is affordable.

**Do NOT reuse room 3's `build_overshoot_bound`** — that is an x-overshoot-and-return table over x classes,
the wrong geometry for a vertical end game.
