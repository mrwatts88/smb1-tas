### Two derivation traps (both cost time here — do not repeat)
- The x subpixel is **`$0400`**. `$0705` is the *speed* fraction (`XFRAC`), not position.
- The model's `y_pos` **low byte is not** the core's `$0433`. Compare via `model_difftest`'s field
  set (XP/XSUB/XSPD/XFRAC/YP/YSPD/YFRAC); never hand-assemble a 24.8 word from RAM.
- `v_force` is an **encoded enum** (`options.rs:362`), so the core's raw `$0709` = 0 is not a legal
  model value. `V_FORCE_AREA_INIT` is right for a control frame — `W84Room3` shows the same pattern.
- Sanity method that caught all of the above: run the identical comparison against **`W84Room3`**,
  which is known-good. If it "fails" too, the comparison is wrong, not the new case.

### RESOLVED: `$0e` is a jumping Green Paratroopa, not a lift

`E_CastleArea6` places **id `$0e`** objects at page 8 cols 11/13 and page 9 cols 11/13 (x 2224, 2256,
2480, 2512); two of them (x 2224, 2256) are inside room 2's span. MrWint's comment calls them "the
pages 8-9 **lifts**" — **that is wrong**. Traced from the WR dump (rows 16008–16088): constant
`Enemy_X_Speed` **−8** (leftward, 0.5 px/frame) with y following a repeating parabolic arc
184 → 141 → 185 → 141 → …, period ≈ 56 frames. That is a **hop**, i.e. `GreenParatroopaJump` exactly
as the ID constants say (`smbdis.asm`, `GreenParatroopaJump = $0e`).

So the port needs **one new class** beyond what already exists: a leftward walker with a periodic
jump arc. Deterministic (no RNG), so a phase counter should cover it — confirm the arc is
frame-indexed rather than player-coupled during the difftest.

### Remaining open question before coding

counter in the slot) or coupled to the player (expensive). The difftest over the WR's 267 frames
answers it directly — that is the first thing to check once the class is stubbed in.
