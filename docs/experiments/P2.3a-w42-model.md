# P2.3a (step 3) — 4-2 in the smb-opt model: cases, generic modes, alignment, three model fixes, validation

Date: 2026-08-22 (session 6). Unit: P2.3a step 3 (STATUS). Engine: `third_party/smb-opt` + `tools/smb-opt-modes.patch`.

## Goal
Put both 4-2 segments (main area → wrong-warp pipe; warp zone → world-8 pipe) into MrWint's player model, make
the search modes case-generic, align the model with the WR dump, and validate against the QuickNES core until
0 differences — so that exhaustive segment bounds for the 4-2 top route (2-frame framerule target, F36) can be run.

## Alignment (F69)

row 199). Hence **model step k from record FIRST ↔ FCEUX row FIRST+2+k ↔ QuickNES frame FIRST−2+k**; the model's root

## Three model fixes found by the WR trace (all read from `data/disasm/smbdis.asm`, all verified on the dump)
1. **Head bump into a brick/question block — `BlockBounceTimer` ($0784)** (F70). `HeadChk` (11946–11973): solid tile or
   water area → `NYSpd`: Player_Y_Speed = 1; otherwise if `BlockBounceTimer` ≠ 0 → `NYSpd` too (no new bounce); else
   `PlayerHeadCollision` sets the timer to $10 (7263–7264) and `BumpBlock` sets Player_Y_Speed = 0 (7307–7314; big Mario's
   `BrickShatter` −2). The fraction (`Player_Y_MoveForce`) is kept in every case. The timer is a frame timer
   (decrements each frame). HappyLee bumps the bottom corridor's ceiling bricks 6 times in a row (rows 6737–6762, dump
   values 16,15,…,0 → 16) and the model diverged 4 frames after the first bump (y speed 0 vs 1). MrWint's model had only
   the `BumpBlock` (=0) path. Now modeled with the timer in the state (`WithBlockBounceTimer`).
2. **Joypad disabled above/below the screen only in water areas** (F71): `PlayerCtrlRoutine` (5558–5571) tests
   `AreaType` first; the model cleared the joypad for every area. HappyLee's warp-zone jump goes above the screen top
   holding A (Y_HighPos 0, rows 7485–7511) and the model dropped A there (y speed −3 vs −4). Now `Swim::IS_SWIMMING`-gated.
3. **Coins end the collision routine for the frame** (F72): `AwardTouchedCoin` → `HandleCoinMetatile` → rts from the
   head, foot *and* side checks, so the frame of a coin touch has no landing / no foot "deep-in-block" impede / no side
   impede. `IgnoreCoins` pretends coins are already gone: the model landed on the bricks next to the bottom-corridor coins a
   frame early (row 6789) and, in a mutated warp-zone trial, pushed Mario +1 px one frame the core did not (f7422: head
   collects the coin at (12,6) while the right foot is in the $19 block). Now `W42MainCoins` (3 coins, row 10 cols 27–29) and
   `W42WarpCoins` (19 coins — every $c2 cell of BB42Warp, checked by script). Keys: main 12 bytes, warp 14 bytes.

## What the dump says about 4-2 beyond the player model
- **Pipe entry (F74)**: `HandlePipeEntry` (12270) = Down held + left foot (X+3) on $10 + right foot (X+12) on $11; the
  model additionally requires no L/R (from `ChkFootMTile`'s branch) or a landing frame. Wrong-warp pipe (col 84): X ∈
  [1348, 1356]; the WR lands on the pipe at X 1343 (row 7168) and walks 5 frames to X 1348 before pressing Down (7173) —
  not a wasted frame: X 1347 would put the right foot at 1359 < 1360. Warp-zone pipe (col 50): X ∈ [804, 812], WR 810.
- **The lift (F73)**: `E_UndergroundArea2` id $27 at page 3 col 10 row 5 = `LargeLiftDown` (8948): spawns at row 6933
  at x 940 (page 3, X 172), y 80; `PlatLiftDown` (8965): Y_MoveForce $f0, Y_Speed 0 → descends 15/16 px per frame
  (`MoveLiftPlatforms`, 10982); a rider is placed by `PositionPlayerOnVPlat` (11846): Player_Y = lift_y − 32, y speed and
  force 0. `PlatformCollisionFlag` ($03A2) is **not** used for it (balance platforms only) — the earlier "WR never stands
  on a lift" check was wrong. The WR rides it rows 7012–7024 (X 954→986, Y 123→132) and jumps off at 7025 from Y 132,
  44 px above the floor, i.e. the lift is the launch pad for the rest of the bottom route. The top route crosses the same
  pit (cols 57–62) while the lift is descending through it, so an exact main-area bound needs the lift (and the scroll,
  for its spawn frame) in the model: **P2.3b**.
- **Enemies**: main area — 3 goombas on the upper floor (page 2 col 14, y $70 group: the top route's floor), green koopa
  page 4 col 13, buzzy beetles page 5 cols 3 and 8; the WR stomps nothing. Warp zone — piranha plants (id $0D) from row
  7480 in slots 0–2; they only kill (never add trajectories), so the enemy-free warp-zone bound is sound.

## Search engine observations
- `bfsc` with all 16 inputs: 1-1 room-1 control (`W11VertPipeEntry`, h(root) = 367, deadline 368 — 1 frame of slack)
  reached 5.2M unique states at layer 60 (×1.14/layer, 39 s/layer, 2 threads) and was stopped; `W42Warp` (h(root) 329,
  deadline 475) 5.0M at layer 21. Killed before the 3 GB cap (`runs/P2.3a/ctrl_w11_d368.log`, `warp_d475.log`).
- MrWint's IDA* (`smb-opt case W11VertPipeEntry`) solves the same control in **22 s, 86 MB, 283,205 states** and returns
  the known 368-frame solution. The difference is his `SmbInputFetcher` (ida.rs:19): a *reduced* input set per state
  (B only on the ground with the current moving direction; L+R only when standing; A only when a jump can start or
  continue; no A|B combinations). It is a domain reduction, not a proven-lossless one, so its results are strong
  heuristic bounds; the full-input BFS stays the proof tool and needs either the external-memory engine (`bfs11c`
  generalised) or a tighter admissible heuristic (the x-only bound leaves ~150 frames of slack on the warp zone because
  the stair climb is vertical work it cannot see).
- `smb-opt case W42Warp` (IDA*, limit 329 upward, 3 GB cap) was killed after 10 min still inside its first limit with a
  140M-state store (`runs/P2.3a/warp_ida.log`): with ~150 frames of slack even the reduced-input IDA* enumerates the
  whole stair region. Conclusion: the warp zone needs a y-aware admissible bound or chokepoint segmentation (P2.3c)
  before any engine can finish it; a candidate found later must be replayed on the core with Down on the entry frame.

## Conclusions
- The warp-zone model is exact (476 WR frames + 30k random/mutated frames, 0 differences) — a pure player-physics
  segment, so `W42Warp` searches give sound enemy-free bounds (piranhas can only remove paths).
- The main-area model is exact up to the lift; the lift (a launch pad the WR actually uses) and the enemies are the
  remaining model content, in that order.
- Three MrWint-model bugs fixed (bounce timer, water-only joypad rule, coins) — none affected the 1-1 third-room
  results (no bricks bumped, no coins, never above the screen there).

## P2.3c (2026-08-22, session 6 end) — measurements for the proof-grade search
- **Reduced inputs do not shrink the proof space much** (`bfsc … --reduced` = MrWint's `SmbInputFetcher` per-state set):
  1-1 room-1 control, deadline 368 (1 frame of slack): full 16 inputs 5.20M unique states at layer 60 (×1.14/layer);
  reduced 2.93M at layer 60, 4.96M at layer 65 (×1.15/layer), 39M visited (`runs/P2.3a/ctrl_w11_d368_reduced.log`).
  MrWint's IDA\* is fast (283k seen) because depth-first search *finds* the 368-frame goal early at the optimal bound, not
  because the f ≤ 368 space is small. A proof ("no 367") must enumerate that space: 10⁷–10⁸+ states per layer for a
  370-frame segment even with reduced inputs → the external-memory engine (`bfs11c` layer files) is required regardless.
- **The warp zone's slack is structural, not physics**: the WR runs at speed 40 from x 82 over the stairs and along the
  roof above the three pipes (Y 32, rows 7568–7628) to x 958, drops past the roof's right end (cols 60–61) and runs *back
  left* 150 px to the world-8 pipe (X 810 at 7724). The x-only bound (329) ignores the forced overshoot-and-return (≈ 60–75
  frames) and the 9-row climb. A staged admissible bound (MrWint's W12Flag pattern): before the drop (on/over the roof or
  left of the stairs) h = steps_x(→ X ≥ 948) + C_ret, after the drop (under the roof, x ≥ 784) h = steps_x(→ X ≤ 812),
  with C_ret = the table's minimum frames from any X ≥ 948 state back to X ≤ 812 — expected slack ≈ 20–30 instead of 147.
  The warp zone's real limiter is the piranha plants (id $0D, rows 7480+) under the roof on the way back: the enemy-free
  optimum is a loose bound there; the useful search needs them.
- **Main area**: with the lift modeled the WR's own path is in the frontier at every checked layer, but the frontier is 9.6M
  at layer 11 from prefix 540 (2 frames of slack): the same space problem. Chokepoints for the top route: the shaft/corridor
  entrance (x ≈ 480, rows 4–6), the lift/pit (x 912–1008), pipe A top (col 72, Y 112), the row-7 bricks (cols 76–77), pipe B.
