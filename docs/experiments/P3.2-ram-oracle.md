# P3.2 — RAM oracle: single-byte perturbation sweep (Track B)

**Unit:** P3.2 (Track B, glitch hunt). Started 2026-08-24, session 17 — a **second, parallel
session**, running alongside a Track A session working P2.2f in the same tree. See
§0 for why that is safe.

**Question.** For each level and each `(address, value)` single-byte perturbation of the 2 KiB
system RAM, does the game reach the ending *earlier* than the WR does? Output: the "jackpot cell"
map, which turns P3.3's write-reachability hunt from an open-ended search ("find any corruption")
into a targeted one ("find a writer to *this* cell").

---

## 0. Why this runs in parallel without touching Track A

Track B needs **no engine sharing**. The oracle runs on the **QuickNES fast core**
(`src/fastcore/`, `build/`, `third_party/QuickNES_Core`) — P1.1's stage-1 core, validated in F45/F46.
Track A's P2.2f work is in `third_party/smb-opt` + `tools/smb-opt-modes.patch`. Different source
tree, different build, different control gate, zero overlap. PROCESS's "exactly one machine edits
the engine" rule is specifically about `smb-opt`; it does not bind Track B.

The real collision surface is git and the shared docs, not code. Protocol agreed with the user
(2026-08-24, session 17) and recorded in STATUS "In progress":

- Track B touches only **new files**: `src/fastcore/ram_oracle.c`, `tools/build_oracle.sh`,
  `docs/experiments/P3.2-ram-oracle.md`, `runs/P3.2/`. It never edits `third_party/smb-opt`,
  `tools/smb-opt-modes.patch`, `tools/build_core.sh`, or any `w*.rs`. A **separate**
  `tools/build_oracle.sh` exists precisely so that `build_core.sh` stays untouched.
- Both sessions commit with **explicit pathspecs — never `git add -A`** (which would sweep the
  other session's in-flight edits into the wrong commit).
- STATUS / log / facts are edited **in place, never rewritten** from a stale read.
- **Fact numbers are split: Track A keeps F135+, Track B reserves F200+.** Without this both
  sessions mint F135 next and collide.
- Resource discipline: single-threaded, `nice -n 10`, under `systemd-run --user --scope
  -p MemoryMax=2G` (the standing "never start a search without a cgroup cap" rule). The box has
  12 cores and ~9 GB available with swap exhausted, and Track A's next step is a d266 bucketed
  beam that wants all 12 threads.

## 1. The ending predicate — exact, and it re-derives F45

`OperMode` (`$0770`) takes exactly three values across the whole WR movie: 0 (title, frames 0–41),
1 (game, 42–17866), **2 (VictoryMode, first at dump frame 17867)**. That first `OperMode == 2`
frame *is* the ending, and it equals 17848 (last input, F16) + 19 (the coast, F17). Measured from
`data/wr/fceux_wr.ram` — see F200.

The oracle computes the same number in-process from the QuickNES core and gets **17864**, i.e.
dump frame 17867 − 3, independently reproducing F45's FCEUX↔QuickNES row origin. That is a free
cross-check of both the predicate and the core alignment.

## 2. Method

`build/ram_oracle` (`src/fastcore/ram_oracle.c`, built by `tools/build_oracle.sh`):

    ram_oracle CORE.so ROM.nes INPUTS.bin --at FRAME [--input-skip 2] [--addr-lo H] [--addr-hi H]
               [--values all|a,b,c] [--cap N] [--no-death-exit] [--all-rows] [--out FILE]

**Pass 1 (baseline).** Run the movie once, recording a per-frame FNV-1a hash of the 2 KiB RAM, the
per-frame lives count, and the victory frame; serialize the core state at `--at FRAME`.

**Pass 2 (the sweep).** For every `(addr, value)`: `retro_unserialize` the saved state, poke
`ram[addr] = value`, then continue with **the movie's own remaining inputs** until one of:

| outcome | meaning |
|---|---|
| `VICTORY` | `OperMode` reached 2. Compare its frame against the baseline's — **earlier is the jackpot.** |
| `CONVERGED` | the perturbed RAM hash equals the baseline hash at the same frame. The perturbation was absorbed; identical RAM under identical inputs ⇒ identical future ⇒ it can never win early. Sound early exit. |
| `DEAD` | lives dropped below baseline, or `OperMode` reached 3 (game over). See the assumption below. |
| `CAP` / `EOF` | frame budget exhausted (default budget = baseline victory frame − `--at`). |

Each row also records `max_opermode`, `max_world`, and the set of `AreaPointer` values seen — so
even a sweep with **zero** victories still produces a map of which cells move the world/area state
machine, which is the actual research output.

**Assumption (stated, not proved).** `DEAD` is an early exit: a run that loses a life is assumed
unable to then finish *earlier than baseline* while replaying the WR's own remaining inputs. This
is what makes the sweep affordable (it cuts the mean run from thousands of frames to ~900). It is
a heuristic about this input sequence, not a theorem. `--no-death-exit` sweeps without it; any
candidate band that looks live should be re-run that way before a claim is made.

## 3. Controls (both pass)

| control | expectation | result |
|---|---|---|
| **Null.** Poke a cell with its own current value (`$075F` = 7 at 8-4). | Detected as identical to baseline immediately. | `CONVERGED(noop)` at frame 0 ✓ |
| **Positive.** Poke `$0770` (OperMode) = 2 directly. | The detector fires with a victory far earlier than baseline. | `VICTORY` at frame 15056, i.e. 2,808 frames early ✓ |
| **Throughput.** | ≈ F46's 15.0k fps. | 14,949 fps ✓ |
| **Alignment.** | Core victory frame = dump 17867 − 3. | 17864 ✓ |

Every `(noop)` row is printed in every sweep, so the null control is re-run continuously — one per
address, for free.

## 4. Which addresses, and why that ordering matters

The obvious failure mode of a RAM oracle is finding cells that "would help if only something else
were possible" — a jackpot with no writer. P3.1 (`docs/oob-audit.md`) already settled the shape of
that risk, and it points at a specific band:

- P3.1 found **one genuine OOB write mechanism**: block-buffer writes for objects above the status
  bar, with a **bounded reach of `$05E0–$06CF`**. A writer demonstrably exists into this window.
- So the **first** sweep is `$05E0–$06CF` (band A, 240 addresses × 256 values = 61,440 runs). Here
  the writer is the *given* and the payoff is the unknown — the useful direction.
- P3.1's "the H7 cells cannot be reached" verdict is **narrower than it reads**: its own §4 excludes
  stack overflow/underflow paths, non-indexed writes, and `VRAM_Buffer` writes indexed by
  `VRAM_Buffer1_Offset` ("a classic corruption vector in other games… not audited line by line").
  So it is not a refutation of H7 by this project's evidence standard, and cells outside band A are
  still recorded — ranked below band A, as **targets for P3.3** rather than as results.

## 8. The `$06CF`-tightness question — answered: the bound is tight (F203)

§6 left H7(c) resting on one question: is P3.1's `$05E0–$06CF` OOB reach bound tight, or could the
block-buffer writer be pushed the 7 further bytes to `$06D6` (WarpZoneControl)? Chased in the
disassembly (no CPU cost, so it ran while the band-A sweeps were going). **Answer: tight, by
arithmetic.**

The mechanism is `sta ($06),y`, with `$06/$07` set by `GetBlockBufferAddr` (smbdis.asm:4328).
Three independent bounds:

**(1) `$07` is always `$05`.** It is loaded from `BlockBufferAddr+2,y` — and `BlockBufferAddr` has
only **two** entries while the index is `tay` after `lsr` ×4, i.e. a **nybble**, 0–15. That looks
like a live out-of-bounds table read (it would let the pointer base come from arbitrary ROM bytes),
and it was the one genuinely promising thing in this routine. It is not reachable: `y = A >> 4` is
bounded to {0,1} at both call sites.

- *Call site 2* — `BlockBufferCollision` (13069), the object path: `A` is assembled as
  `(page_lsb << 4) | (x >> 4)` via `and #$01 / lsr / ora $05 / ror / lsr / lsr / lsr`, so `A ≤ 31`.
- *Call site 1* — `RendBBuf` (3266), the renderer: passes `BlockBufferColumnPos` ($06A0). Its only
  two writers keep it ≤ `$1F`. The area initializer (2680) does **`and #%00000001` before** its four
  `asl`s → 0 or `$10` (the comment "store LSB of page number" is accurate; the mask precedes the
  shifts, so the upper page bits never survive). `IncrementColumnPos` (3069) does
  `and #%00011111` after every `inc`.

**(2) `$06 ≤ $DF`.** `GetBlockBufferAddr` does `pla / and #%00001111 / clc / adc BlockBufferAddr,y`,
so the low byte is `{$00|$D0} + col` with `col ≤ 15`. `$D0 + $0F = $DF` — no carry into `$07`.

**(3) `y ≤ $F0` = 240.** The object path computes
`y = ((SprObject_Y_Position + BlockBuffer_Y_Adder) & #%11110000) − $20` (13074–13078). The `& $F0`
leaves `$00…$F0`, so the values that wrap negative through `sbc #$20` are `$D0` (row 13), `$E0`, and
**`$F0` = 240, the maximum**. The area-parser path (`StrBlock`, 3282) cannot go out of bounds at
all: its `y` starts at 0 and steps `adc #$10` under `cpx #$0d`, so `y ≤ 192` and its highest address
is `$069F` — exactly the last byte of Block_Buffer_2.

**Ceiling = `$0500 + $DF + $F0` = `$06CF`.** An arithmetic maximum of the mechanism, not an estimate.

**What this does and does not settle.** It closes *one mechanism* against *one target*: the only OOB
writer P3.1 found cannot reach `$06D6` (7 bytes short), and is 144 bytes short of `$075F`
WorldNumber. It is **not** a refutation of H7 — by this project's evidence standard a refutation
would have to cover every writer, and P3.1 §4 explicitly leaves three classes unaudited: stack
overflow/underflow paths, non-indexed writes, and `VRAM_Buffer` writes indexed by
`VRAM_Buffer1_Offset` ("a classic corruption vector in other games… not audited line by line").
H7 now reduces cleanly to **the writer hunt** (P3.3), with the payoff side priced by this unit.

## 9. Predicate correction (F204) — `OperMode == 2` is an *axe* detector, not an *ending* detector

Found while chasing §8. `VictoryMode` is entered at **every** castle axe: `VictoryModeSubroutines`
(1122) runs `BridgeCollapse → SetupVictoryMode → PlayerVictoryWalk → PrintVictoryMessages →
PlayerEndWorld`, and only `PlayerEndWorld` terminates, only when `cpy #World8 / bcs` passes. Below
world 8 it resets `AreaNumber`/`LevelNumber`, increments `WorldNumber`, and puts `OperMode` back to
game mode.

`ram_oracle` now requires **`OperMode == 2` and `WorldNumber >= 7`** for `VICTORY`, and records any
sub-world-8 axe in a new `axe_frame` column *while continuing the run* — an off-route axe is itself
a notable event (it is the F201 / D2 route question showing up empirically). Both controls re-pass
after the change.

**The two band-A sweeps launched before this fix remain sound.** They cannot produce a false
negative: every real ending is preceded by `OperMode == 2`, which the old predicate stopped on. They
could only *mis-label* a hit — and both have zero hits; any that appears in the remainder is
checkable against the row's `max_world`. Left running rather than restarted, deliberately.
