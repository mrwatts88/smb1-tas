```

```
`runs/P2.5b/w11_d367.log` — heuristic built in 4.7 s, **at root: Some(367) steps (deadline 367)**;
frontier 1 → 36 states over layers 1–20, then

```
layer 21: parents 36 -> unique 0, generated 0, pruned 576, ...
no live states left after layer 21
total 4.7s
no goal found within 367 steps
```

Every one of the 576 children at step 21 fails `step + 1 + h > 367`. Total cost: **4.7 seconds** —
the room-1 search is trivially small at zero slack, not the ~5M states/layer F82 predicted (that
estimate was for one frame of slack, see §3).

### 2. The positive control — it runs *before* the search, and it already passed

`--check-path N` (main.rs:938–950) replays N input records as a reference path and, per step,
(a) evaluates the goal test, (b) checks the bound against the path itself
(`if k + 1 + hh > check_path { BOUND VIOLATION }`). This executes at startup, before layer 1. The
abandoned d368 run (§3) therefore already produced the complete control:

```
reference path: step 368 x 0x39410 y 0x170c0 xspd 0x1f1c ... h Some(0)
                result StateChangeVerticalPipe(57, 7) GOAL
reference path: 0 bound violations over 368 steps (reference length 368)
```

- the WR's own 368 inputs replay in the **enemy-aware** model with every step `Success` — two
  `object event Stomp` at steps 126 and 320 (the goombas the WR bounces off), no death, no divergence;
- the goal test fires at **exactly** step 368 on `StateChangeVerticalPipe(57,7)`;
- **0 bound violations over all 368 steps** ⇒ at deadline 368 the bound never prunes the true optimum;
- the exhaustive part additionally confirmed `reference path step N in the frontier` for **layers 1–90**
  before it was stopped.

So the dry at 367 is not a broken-search artifact: the same case, bound and goal test accept the
WR's 368 line end to end.

### 3. Why the d368 exhaustive rung was abandoned (and why it was never needed)

Launched as planned, it could not finish on this machine:

| layer | frontier (unique) | layer file | growth |
|---|---|---|---|
| 80 | 32.9M | 3.0 GB | |
| 85 | 38.1M | 3.4 GB | |
| 90 | 61.3M | 5.6 GB | ×1.10/layer |

94 GB of layers at layer **90 of 368**, 43 min in, still growing. Disk headroom to the watchdog
floor was 105 GB ⇒ ~10 more layers. Even had growth flattened at 61M/layer, the remaining 278
layers needed **≈1.6 TB** and ≥12 h. Killed (pids 599229 search / 599883 watchdog); layer dir
deleted (94 GB reclaimed), `runs/P2.5b/w11_d368.log` kept as the record.

The blowup is expected and is *not* evidence of a bad case: at deadline 367 a state must satisfy
`k + h = 367` exactly (zero slack → 36 states), while at 368 it may sit one frame behind the
optimistic line — and `h` is a coarse x-only bound, so tens of millions of distinct states qualify.
The exhaustive d368 rung would only have re-derived, at 1.6 TB, what the reference-path audit
established in 4.7 s.

### 4. Soundness: why the pruning is valid *with enemies*

The search prunes exactly one way (main.rs:1029): `if step + 1 + hh > max_steps`. So the dry is a
proof iff `h` is admissible. Four links, all code-level:

1. **The goal forces the bound's x.** Entry fires only when the **left** foot hits `cv == 0x10` at
   cell (57,7) *and* the **right** foot hits `cv == 0x11` (emu.rs:468/485). With
   `BLOCK_BUFFER_X_ADDER_DATA[0x10] = 0x0c00` (12 px, small Mario) the right-foot condition
   `(x_pos + 0xc00) >> 12 == 58` gives **`x_pos ≥ 0x39400`**, and the left-foot condition caps it
   below 0x39d00. The case's bound is `get_steps_until_x_pos_at_least(s, 0x39400)` (case/w11.rs:580)
   — the entry threshold *exactly*, so it cannot demand more x than the goal does.
2. **The x table is a validated lower bound** on the x-motion state machine (MrWint's
   `XPosHeuristic`; audited against the core in F68 — 1,906,600 checks, 0 violations).
3. **Enemies cannot invalidate an x-only bound.** `src/w11enemies.rs` contains no reference to
   `x_pos` or `x_spd` anywhere; the module's only write to the player state is line 315,
   `s.y_spd = (-4i16 << 8) | (s.y_spd & 0xff)` — the stomp bounce. A stomp changes y speed only, a
   hit is `LiftEvent::Death` (pruned as dead). So the x machine the table is computed over is
   precisely the one the enemy-aware search steps.
4. **The model equals the game** on this room: WR replay 368/368 with 0 differences, plus 500
   random trials / 82,234 frames / 0 differences / 53 matching deaths / 169 stomps (§Validation).

⇒ `h` is admissible under `--enemies`, the pruning is sound, and **no path from the room-1 control
state reaches the warp pipe in ≤ 367 frames.** The WR's 368 is optimal.

### 5. Bonus forensics: where 1-1's last frame goes

`k + h` along the WR's line is **367 for steps 1–20** and **368 from step 21 to the goal** — one
transition, never another:

```
step 20  x 0x3700 y 0x1a930 xspd 0x17c0 JUMPING  h 347   k+h = 367
step 21  x 0x3880 y 0x1ad30 xspd 0x18f0 JUMPING  h 347   k+h = 368  <- the frame
step 22  x 0x3a00 y 0x1b0a0 xspd 0x18f0 STANDING h 346   k+h = 368
```

Step 21 is an airborne frame of the opening jump that buys no progress in the x table's terms, and
Mario lands at step 22 with x_spd frozen at 0x18f0. The d367 dry says this is *forced*: **every**
reachable state has lost the frame by step 21. The optimistic x-only bound of 367 is unachievable
because the table ignores the ground/air geometry that the opening jump imposes; 368 is the truth.
The WR then rides the bound exactly — `k + h = 368` for all 347 remaining steps — and enters the
pipe at x 0x39410, **0x10 (1/16 px) past the 0x39400 threshold**: the earliest pixel that admits entry.

### 6. Scope of the claim

Proof-grade for the modeled space, with the documented exclusions:
- the **(21,7) powerup bump is refused** (`LiftEvent::ItemBump` → pruned): a mushroom object is

- states falling below `y_pos ≥ 0x1d000` are pruned as dead (pit), and enemy contact is death.
- the koopa (page 6) is unreachable before the pipe (F64), so no kick path exists here.
