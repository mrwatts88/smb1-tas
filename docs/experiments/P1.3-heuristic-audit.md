# P1.3 — Is MrWint's x-bound sound against the real game?

**Question.** Every search prunes a state when the XPos table says it cannot reach the target x in the remaining
steps. The table is computed from the *model*. Does the *real game* (QuickNES core) ever gain more x in k frames
than the table allows from the same state? If yes, every "no path" proof is unsound.

**Method.** `smb-opt trace11bound FIRST N FILES…` (new mode): runs the 1-1 third-room model on input files and, after
every step, prints the table's max x gain in 1..40 further steps from that state, classified exactly as the search
classifies it (`XPosHeuristic::to_x_pos_state`: x speed+fraction, |speed| class, moving/facing dir, on-ground,
running flag). `tools/heuristic_audit.py` builds random-input trajectories (the WR's records to the root, then random
A/B/L/R with given probabilities), runs the core (`build/harness`, RAM per frame) and the model on each, asserts the
model's x equals the core's at every step (it did, on every step), then checks core_x(t+k) − core_x(t) ≤ bound_k(t)
for all t and k ≤ 40 until a death/grab/non-Success. Unknown classes ('?', never pruned by the search) are counted.

**Runs (2026-08-22, `runs/P1.3-heuristic-audit/`).**
| root (record) | inputs | trials × frames | steps | checks | violations | unknown | bound attained exactly |
|---|---|---|---|---|---|---|---|
| 1048 (room entry) | pr .75 pl .15 pa .25 pb .6 | 10 × 150 | 970 | 30,600 | 0 | 0 | 1,071 |
| 1048 | same | 200 × 200 | 20,522 | 656,880 | 0 | 0 | 25,499 |
| 1232 (stairs/pole) | same | 200 × 80 | 13,000 | 356,000 | 0 | 0 | 135,600 (38%) |
| 1048 | L/R-heavy: pr .55 pl .45 pa .35 | 200 × 150 | 25,678 | 863,120 | 0 | 0 | 13,809 |
Total: 1,906,600 checks, **0 violations**, 0 unknown classes; max gain/bound ratio 1.0000 (the bound is tight: the
real game reaches it, never exceeds it).

**Conclusion (F68).** In the 1-1 third room the x-bound is sound and tight against the real game for every tested
state class, including L+R accelerations, turnarounds, jumps, goomba stomps and the staircase. Caveats: (1) this is
sampling, not proof — but it tests the bound *as used*, classification included, against the core, not the model;
(2) room-3 geometry only: other rooms can only add obstacles (which cost x) unless a mechanic moves Mario's x other
than his own speed — lifts/platforms (4-2, 8-x) remain the one open case (STATUS "Model omissions"); (3) extending
the audit to other rooms needs either the generalized trace (P2.3a's `bfsc`/trace for any case) or a RAM-side
classifier; cheap to run whenever a new case exists.
