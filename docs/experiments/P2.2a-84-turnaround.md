## Session 15 — the room is cut at the apex; the return leg is proven optimal

Started on the queued `w84enemies` port, and stopped before writing it: two cheaper findings changed
the plan, and one of them says the port is more expensive than the checkpoint assumed.

### 1. The return leg (apex → pipe) is at its bound: 33, and H25's frame is not there

Cutting the 195-frame room at the WR's **apex** (max x 3457, speed crossing 0 — record 16516 =
prefix 162) makes the tail a 33-frame segment, comfortably inside the runbook's segmentation ruler:

| rung | command (prefix 162 from record 16354) | result |
|---|---|---|
| control | `… 16354 162 33 --check-path 33` | `at root: Some(33)`, **0 bound violations over 33 steps**, **96 goals at layer 33**, 7.7 s |
| record | `… 16354 162 32` | **dry** — `no live states left after layer 1`, `no goal found within 32 steps`, 10.6 s |

`h(apex) = 33` and the WR spends exactly 33 ⇒ **the return leg sits on its bound with zero slack.**
The d32 rung dies at layer 1 for that reason. So from the WR's apex state the turnaround-and-enter is
optimal, and **H25's frame cannot come from the return** — it must come from the approach, or from
arriving at a *different* apex state. (`runs/P2.2a/w84r3_apex_d33.log`, `w84r3_apex_d32.log`.)

### 2. A real hole in the case bound: `Some(0)` left of the pipe window (fixed)

`W84Room3::distance_to_goal_heuristic` was three-branch, and the third was `Some(0)`:

```rust
} else if s.x_pos > W84R3_PIPE_XMAX {
  Some(self.h.get_steps_until_x_pos_at_most(s, W84R3_PIPE_XMAX))
} else { Some(0) }        // <- every state left of the window
```

Any state with `SL ≥ 3345` and `x ≤ PIPE_XMAX` scored 0 — admissible, but it can never prune, and
Mario turns around only 53 px right of the pipe, so a large part of the frontier crossed into that
half-plane and became immortal. The missing edge is the window's *left* rim, and it follows from the
same foot geometry that closed 1-1 today (F124): entry needs the left foot on `cv 0x10` in col 212
**and** the right foot on `cv 0x11` in col 213, so with the small-Mario adders 0x300 / 0xc00,
x ∈ [0xd3d00,0xd4d00) ∩ [0xd4400,0xd5400) = **[0xd4400, 0xd4d00)**. `PIPE_XMAX` was already the top
edge; `W84R3_PIPE_XMIN = 0xd4400` (3396 px) is now the bottom, with the leftward-overshoot branch:

```rust
} else if s.x_pos < W84R3_PIPE_XMIN {
  Some(self.h.get_steps_until_x_pos_at_least(s, W84R3_PIPE_XMIN))
} else { Some(0) }
```

Sound (re-entering the window is necessary for entry) and it plugs the left-overshoot leak. The
residual `Some(0)` *inside* the 9-px window is honest for an x-only bound — tightening it needs a
y-coupled gate (the 4-2 `ygate` pattern), since entry also requires falling onto the pipe's top.

### 3. Correction: `--stop-step`/deadline units — `max_steps` is layers from the POST-prefix root

The first apex rung was launched as `… 16354 162 195` on the reasoning that 195 is the WR's frame
count for the room. Wrong: `bfscx`'s `max_steps` counts layers from the root *after* the prefix, so
that rung had 195 − 0 = 195 layers of budget against `h = 33` — **162 frames of slack**, and it
blew up exactly as slack-11 and slack-29 rungs did (`pruned 0` on every layer, 100M states / 27 GB
at layer 23 before it was killed). The correct deadline for a prefix-162 rung is 33. Cross-check:
the 4-2 control gate `… 6584 575 587` is prefix 575 / deadline 587 and stops at layer 10 **because
it found goals**, not because 587 bounded it. Recorded as a runbook rule — this mistake is cheap to
make and expensive to run.

### 4. The whole-room d194 rung is not feasible, and the horizon is not why

With the bound fix in: `at root: Some(183)` against deadline 194 ⇒ **slack 11**, which the frontier
law (F98) puts far outside laptop range. The obvious suspect was the overshoot horizon (96 steps,
while the approach is ~162), since everything past the horizon is extrapolated at max speed — but
rebuilding at **horizon 200 leaves the root bound at 183 exactly**. So the 12-frame gap between the
bound and the WR's 195 is genuine looseness from terrain and the y-coupling of pipe entry, not
truncation — precisely F95 ("the x-only bound cannot carry a >~150-frame open-terrain segment").
**The room must be searched in chained segments, not whole.** The apex cut above is the first one.

### 5. The cheep frenzy is state-coupled, NOT frame-indexed — the port is bigger than budgeted

The checkpoint's plan rested on "id $14, LFSR-driven = frame-indexed on the lag-free route". The LFSR
is frame-indexed, but the spawn law is not a function of the frame alone. `InitFlyingCheepCheep`
(smbdis.asm:8419) reads **`Player_X_Speed`** (branching on `cpy #$19` to double a seed term) and
**`Player_X_Position` / `Player_PageLoc`** — the cheep's x is `Player_X ± FlyCCXPositionData[y]`, its
speed comes from `FlyCCXSpeedData[y]`, and its direction can flip on the LFSR's d1. So spawns are
placed *relative to Mario* and parameterised by his speed, and `FrenzyEnemyTimer` must be carried in
the ext. Consequences: (a) two search trajectories that differ in x or speed see **different cheep
fields**, so the enemy ext genuinely multiplies the state space rather than riding along as a frame
index; (b) `MoveFlyingCheepCheep` (asm:9922) adds a `PRandomSubtracter`-indexed arc on top. This is a
substantially larger job than the goomba port was, and it should not be started until a rung exists
that is decidable *without* it — see the plan below.
