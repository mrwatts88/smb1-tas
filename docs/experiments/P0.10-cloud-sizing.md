## 2. Billing mechanics (verified 2026-08-22)

Source: <https://docs.hetzner.com/cloud/billing/faq/>; rates from the authenticated API
(`GET https://api.hetzner.cloud/v1/pricing`, USD, net).

| rule | detail |
|---|---|
| granularity | **hourly, rounded up** — a 20-minute box costs a full hour. No daily minimum. |
| monthly cap | charged the *lower* of (hours × hourly) or the monthly price. ccx63: 744 h × $1.6138 = $1,200.67 → capped at **$1,006.99** (−16%). |
| **powered-off servers still bill** | *"We will bill you for your servers until you delete them, independent of their state."* Resources stay allocated. **`hcloud server poweroff` saves nothing — the off switch is `hcloud server delete`.** |
| snapshots (`image`) | **$0.0199 / GB-month**, on the *compressed* size. |
| volumes | **$0.0767 / GB-month**, billed while the volume exists (attached or not). |
| primary IPv4 | **$0.60 / month**, billed separately from the server. IPv6 free. Let it auto-delete, or `hcloud server create --without-ipv4`. |
| automatic backups | flat **20 % of the server price**. Do not enable — layer files are reproducible and code is in git. |

Two things fall out of this table:

- **Across dedicated tiers, $/core-hour is flat to within ~6 %** (0.0315–0.0336; the 2/4-core boxes are ~25 %
  worse). There is no economy of scale, so machine size buys wall-clock only, and the $300 cap is
  ~9,000 dedicated-core-hours however it is sliced.
- **The shared tiers are 4–10× cheaper per core.** cx53 offers 16 cores for $0.0561/h — *one fifth* the price
  of the 8-core ccx33, with twice the cores and more disk. Hetzner's own framing is that shared plans give
  "baseline performance with the option to temporarily burst above the baseline", i.e. our sustained-100 %-on-
  every-core-for-days workload is not what they are sold for; the FAQ states no explicit prohibition or
  fair-use threshold, so the honest status is **unknown contention, unknown tolerance** rather than "not
  allowed". Given the price gap this is worth *measuring*, not assuming — see §6.

## 4. How the engine scales (measurement, not estimate)

`bfscx_run` / `bfs11c_run` (`third_party/smb-opt/src/main.rs`, expansion loop ~line 1165, merge ~line 1272):

- **Expansion is embarrassingly parallel**: `--threads N` threads each take a slice of the parent layer file,
  expand 16 inputs per parent, sort/dedup a private accumulator, and spill sorted runs to `<layer-dir>/tmp/`.
- **The k-way merge is single-threaded**: one `BinaryHeap<Reverse<(Rec, usize)>>` drains all runs into the next
  layer file. This is the only serial phase, and it is what caps useful core count.

Measured on run 4's big layers (`runs/P2.1b-model/room_compact_d238_r85.log`, i5-1335U, `--threads 12`,
`--acc-mb 256`, ~700 M unique states/layer):

```
layer 137: parents 707,763,737 -> unique 710,561,960, generated 10,530,932,403;
           1476.2s (expand 1401.0s, merge 75.3s of 48 runs)
layer 141: parents 637,621,010 -> unique 622,652,022, generated  9,182,221,074;
           1014.7s (expand  978.2s, merge 36.6s of 43 runs)
```

Serial fraction at 12 laptop threads: **~4–6 %** (36–75 s merge against ~1,000–1,400 s expand). Parallel work
per big layer ≈ 1,200 s × 12 ≈ **14,400 laptop-core-seconds**.

Amdahl projection, **assuming a Hetzner dedicated core ≈ 1.6× an i5-1335U E-core** (an *assumption* — see §7):

| cores | wall / big layer | speedup vs laptop | merge share |
|---|---|---|---|
| 16 (ccx43) | ~610 s | 2.1× | 8 % |
| 32 (ccx53) | ~330 s | 3.8× | 15 % |
| 48 (ccx63) | ~235 s | 5.4× | **21 %** |
| 64 (hypothetical) | ~190 s | 6.7× | 26 % |

**48 is the knee.** Past it, a growing share of the cores idle through the merge — and with flat per-core
pricing that idle time is spent budget, not just lost time.

**This table is currently aspirational**: the account quota caps us at 8 dedicated cores (§3), where the model
gives ~1.08× the laptop. It stays here because it is the analysis that decides the machine *once the limits
increase lands*, and because it is what says the merge does not need parallelising at the sizes we can reach
today.

Two mitigations, both cheap:
- **`--acc-mb`.** Run 4 used 256 MB/thread and spilled 43–49 runs per layer. ccx63's 192 GB allows
  `--acc-mb 3000` at 48 threads (144 GB), cutting the run count to single digits and shrinking the merge
  substantially. This is the free half of the fix and should be in the first big run.
- **Parallelising the merge** (not done — new sub-unit **P2.3c-3**). If the expansion threads bucket their
  output runs by the top bits of the key, each bucket merges independently and the next layer file is the
  buckets concatenated in key order. That removes the serial phase entirely and makes ≥ 64 cores worthwhile.
  Contained change to `bfscx_run`; worth doing *before* committing hundreds of core-hours.

## 5. Disk

- A 700 M-state layer file is 700e6 × 16 B = **11.2 GB raw**; transient sorted runs in `tmp/` add roughly as
  much again during expansion.
- Run 4 is at **47 GB for 143 layer files** only because `tools/room_compress.sh` xz's all but the newest two
  (~5.5 GB raw → ~200 MB). Any cloud run must run the same compressor alongside.
- **At the current quota this is the binding constraint, not CPU.** ccx33 has 240 GB of local disk and cx53
  320 GB, against run 4's ~11 GB raw per layer (47 GB for 143 layers only because of xz compression). 4-2 main
  is ~587 frames against run 4's 238 and its frontier bound is not yet known (P2.3c-2c), so a main-area run on
  a reachable tier almost certainly needs a volume: at $0.0767/GB-month, 300 GB is $23/month (~$0.77/day).
  ccx63's 960 GB would have absorbed it locally — another thing the limits increase buys.

## 6. Recommendation (revised for the 8-core quota)

**The headline: a single ccx33 is not worth buying to replace the laptop.** At 8 dedicated cores the Amdahl
model gives 9,000/8 = 1,125 s expand + ~50 s merge ≈ **1,175 s per big layer against the laptop's 1,268 s —
about 1.08×.** Eight dedicated cores are roughly one laptop. Paying $0.26/h to move run 4 (which is ~1.5 days
from finishing) onto a box that is 8 % faster is not a trade worth making.

So the near-term plan is not "a bigger box", it is:

1. **Let run 4 finish on the laptop.** Nothing available beats it enough to justify the migration risk.
2. **Benchmark the shared tiers — it costs cents.** One hour of cx53 is **$0.06**; cpx51 $0.13; ccx33 $0.26.
   Run the `bfscx` 4-2 WR-suffix control and a `--resume` of a run-4 layer on each, and compare expand
   throughput (generated states/s) against the laptop's logged numbers. If a 16-core cx53 delivers even half
   of dedicated throughput it is ~2× the laptop at **1/5 the price of ccx33** — the single highest-leverage
   measurement available right now, for under a dollar total. If it delivers full throughput, it is ~2.1× the
   laptop at $0.0561/h, which changes the whole economics of the 4-2 proof.
3. **Scale horizontally, not vertically.** The searches that are currently *queued* behind each other on the
   laptop — P2.5b's segment searches, the `tools/bfscx_ladder.sh` deadline ladder, warp zone vs main area —
   are independent jobs needing no shared state. N small boxes run N searches with zero engineering, which is
   exactly the shape that small-instance quotas and flat per-core pricing suit. This is the real near-term win
   and it does not need a limits increase.
4. **Re-request the limits increase once the account ages** (Hetzner typically opens this up after some
   history and a paid invoice). Revisit ccx53/63 for the 4-2 main-area proof then — §4's knee analysis stays
   valid for that decision, it is just not actionable today.
5. **Deprioritise P2.3c-3 (parallel merge).** At ≤ 16 cores the serial merge is only ~4–6 % of wall time; it
   only becomes worth the code change at 32+ cores, i.e. after the limits increase. Recorded as a sub-unit but
   parked.

Indicative costs against the $300 cap:

| action | cost |
|---|---|
| shared-tier benchmark (1 h each of cx53 + cpx51 + ccx33) | **~$0.46** |
| ccx33, 24 h segment-search burst, then delete | ~$6.27 |
| cx53, 24 h segment-search burst, then delete (if it benchmarks well) | ~$1.35 |
| 300 GB volume parked between runs | ~$0.77/day |
| **an 8-core box left running and forgotten** | $6.27/day — the cap in ~48 days |

The forgotten-box failure mode is far less dangerous at this quota than it would have been at ccx63
($38.70/day), but the operational rules still apply and go into STATUS:
- Delete (not power off) at the end of every run — **`poweroff` does not stop billing** (F95).
- `hcloud server list` at session start, every session, so a stray box is visible in the orient step.
- Record every spend in STATUS "Spend" as it happens.

## 7. Open questions / what this does not establish

- **Whether the shared tiers are quota-limited too.** The user reported the restriction on *dedicated*; cx53 /
  cpx51 / cax41 availability is unconfirmed. First thing to check at create time.
- **Whether sustained full-load use of a shared tier is acceptable to Hetzner, and what contention does to
  throughput.** Both unknown; the FAQ neither permits nor forbids it explicitly. The benchmark in §6.2 answers
  the throughput half cheaply. If we intend to run a shared box flat-out for days, that is worth asking
  Hetzner support directly — **and that counts as outreach, so it needs the user's go-ahead first** (CLAUDE.md).
- **The 1.6×/core factor is unmeasured** and everything in §4 scales with it. The §6.2 benchmark replaces it
  with a measurement.
- The Amdahl model assumes expansion scales linearly. It will not, quite — the per-thread sort is
  memory-bandwidth bound. Treat §4 as an upper bound on speedup. (At 8–16 cores this matters much less than it
  would at 48.)
- **No measurement yet of the 4-2 main-area frontier size** (P2.3c-2c), so the *total* core-hours for the
  main-area proof — the number that decides whether it fits in $300 at all — is still unknown. **This unit
  sizes the machine, not the run.** With the quota capped at 8 dedicated cores, that question gets sharper,
  not softer: if the main-area proof needs ~9,000 core-hours it is 47 days on a ccx33.
- **ARM (`cax41`)** is untested and needs a rebuild plus a fresh `model_difftest` pass before any result from
  it could be trusted. Parked, not refuted — at $0.0049/core-hour it is worth revisiting if x86 shared tiers
  disappoint.
- Disk: ccx33 gives only 240 GB against run 4's 47 GB-compressed / ~11 GB-raw-per-layer profile. A big run on
  this tier needs `tools/room_compress.sh` running alongside and probably a volume.
