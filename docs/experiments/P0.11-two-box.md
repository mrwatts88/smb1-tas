# P0.11 — the Mac as a second (overflow) host

**Question.** The project has run on one box (`laptop`, Fedora, i5-1335U). A MacBook Pro is on
the same LAN with key auth both ways. Can it carry search/validation load, and how should two
machines be driven from one agentic session?

**Answer.** Yes — the Mac is an operational overflow host as of 2026-08-23, running everything
through an arm64 Linux container:
the Mac cannot run `smb-opt` natively, and the reason is a hard linker incompatibility, not a
configuration mistake (§2). `docker build` is broken on this Mac, so the image is built on the Linux
box and shipped over (§4). The control gate passes exactly (§5).
The work protocol is in PROCESS.md "Parallel work on the second host"; the decision is
D-2026-08-23 in `docs/decisions.md`.

---

## 1. Capacity and a throughput proxy

| | Fedora `laptop` | Mac |
|---|---|---|
| CPU | i5-1335U, 2 P + 8 E = 12 threads | M3 Pro, 6 P + 6 E = 12 |
| RAM | 15 GiB | 18 GiB |
| Free disk | 163 GB on `/home` | 539 GB |

Proxy benchmark — 200M LCG steps plus two random accesses into a 64 MB table, `cc -O2`,
single-threaded. Chosen to resemble `bfscx`'s state churn plus dedup probing. **This is a
proxy, not the engine**; it is superseded by the P0.11a control run.

```
cc -O2 -o bench bench.c && ./bench        # identical source on both hosts

Fedora i5-1335U, native x86_64     3.78 s   (nice -n 19, sharing the box with live jobs)
Mac M3 Pro, x86_64 under Rosetta   3.69 s   ~= 1.0x the Fedora box
Mac M3 Pro, native arm64           1.34 s   ~= 2.8x the Fedora box
```

Caveats: one sample each; gcc 15.2.1 vs Apple clang 21; the Fedora run was `nice`d and shared
the machine; core assignment (P vs E) not pinned. The M3 Pro is 6 P + 6 E, so aggregate is
roughly 8.4 P-core-equivalents, not 12.

## 2. The Mac cannot run smb-opt natively — proof

`smb-opt` pins Rust `nightly-2018-06-01`, which predates Apple Silicon.

```
https://static.rust-lang.org/dist/2018-06-01/rust-nightly-aarch64-apple-darwin.tar.gz -> 404
https://static.rust-lang.org/dist/2018-06-01/rust-nightly-x86_64-apple-darwin.tar.gz  -> 200
```

So the only macOS-native option is the x86_64 toolchain under Rosetta 2. It **compiles** but
**cannot link**. Apple's current linker (`ld-1267`, built 2026-06-08) rejects the 2018 rlib
layout, in which crate metadata is a plain archive member rather than an object file:

```
ld: in .../liballoc_system-41d035b456efd594.rlib(rust.metadata.bin), archive member
    'rust.metadata.bin' with length 13420 is not mach-o or llvm bitcode file
```

Tried and still failing:
- `-C link-arg=-arch -C link-arg=x86_64` — fixes a *separate* problem (rustc targets x86_64
  while `cc` defaulted to arm64: "found architecture 'x86_64', required architecture 'arm64'"),
  but does not touch the metadata rejection.
- `-Wl,-ld_classic` — the classic linker still exists (deprecated) and still rejects it.
- `-C prefer-dynamic` — same failure.
- Running the whole build under `arch -x86_64` — the `~/.cargo/bin` shims are arm64
  ("Bad CPU type in executable"); invoking the toolchain's own x86_64 `cargo` directly reaches
  the same linker error.

**Conclusion:** the Rosetta path is dead for this toolchain, and the ~1.0x figure in §1 is
moot. Native arm64 macOS would require porting off nightly-2018-06-01 (P0.11c) — untried.

## 3. The design: an arm64 Linux container

`nightly-2018-06-01-aarch64-unknown-linux-gnu` **does** exist (HTTP 200), and Linux's linker
accepts the 2018 rlib layout — the Fedora box builds it daily. So an arm64 Linux container
builds natively on the Mac, at the §1 native-arm64 speed, with no Rosetta penalty.

Three further benefits:
- `docker run --memory=N --memory-swap=N` is a **real cgroup cap** — the Mac's answer to
  STATUS's "never start a search without a cgroup cap" rule, which `systemd-run --scope
  -p MemoryMax=` provides on Linux and macOS has no equivalent for.
- The project's existing Linux-only scripts (`tools/build_core.sh`, the QuickNES core, the
  C harness) run unchanged, because the container *is* Linux.
- Build provenance is pinned by the image tag plus the commit the patch came from.

Artifacts: `tools/Dockerfile.smbopt`, `tools/mac_run.sh` (cap + mount + run),
`tools/watchdog.sh` (portable frontier/disk watchdog, generalises
`runs/P2.3c-2c/watchdog_d149.sh`).

**The binary built in the container is an arm64 Linux ELF.** It cannot be run from the macOS
shell; every invocation goes through `tools/mac_run.sh`.

## 4. Docker on this Mac cannot pull or build images — worked around

**Resolved 2026-08-23: the Mac is operational.** The workaround stands as the supported route;
the underlying Docker fault was not fixed.

What works on this Mac's Docker (27.5.1, aarch64, 12 CPUs, 8.2 GB VM): `docker run` on a local
image, `docker load` from a tarball, and container networking (from inside a container, raw
IPv4 and DNS-resolved TCP both connect).

What does not:
- `docker pull` — hangs against Docker Hub *and* the AWS ECR mirror, before and after a full
  Docker Desktop restart. In-VM DNS returns **IPv6-only** addresses for Hub, consistent with a
  VM lacking IPv6 egress.
- `docker build` — hangs in **every** variant tried, even with the base image already local and
  no network required: BuildKit default (at `load metadata`); BuildKit `--pull=false` (at
  `#4 resolve <digest>`); the legacy builder; and the legacy builder with an **empty build
  context**, which rules out slow virtiofs context transfer.

### The route that works: build the image on the Linux box, ship it
The Fedora box has podman and working egress, and with `qemu-user-static` installed it builds
arm64 images under emulation. The Mac then only needs `docker load` and `docker run`, both of
which work.

```sh
# on the Fedora box (needs qemu-user-static; nice it — the box runs searches)
scp tools/Dockerfile.smbopt laptop:/tmp/
ssh laptop "mkdir -p /tmp/emptyctx && nice -n 19 podman build --platform linux/arm64 \
            -f /tmp/Dockerfile.smbopt -t smb-opt-build:2018 /tmp/emptyctx"
ssh laptop "nice -n 19 podman save --format docker-archive \
            -o /home/mattwatts/smbopt-arm64.tar localhost/smb-opt-build:2018"

# on the Mac
scp laptop:/home/mattwatts/smbopt-arm64.tar /tmp/ && docker load -i /tmp/smbopt-arm64.tar
docker tag localhost/smb-opt-build:2018 smb-opt-build:2018   # podman keeps a localhost/ prefix
```

Image is 1.59 GB; the emulated build took ~25 min, the transfer seconds (F110). `podman save`
writes to home rather than `/tmp` on purpose — `/tmp` may be tmpfs, and that box is memory-tight.

**This only has to be redone when the *image* changes** (a Dockerfile edit). Engine changes do
not need it — see §5.

### VM memory — raise it in the GUI, not the config file
The Docker VM was at **7.65 GiB** of the Mac's 18 GiB (Docker Desktop's ~50% default); it was
**raised to 12 GiB on 2026-08-23** via the GUI, reporting 11.67 GiB usable. Raising it is
worthwhile but modest: it buys bigger `--acc-mb` accumulators and
more page cache for the merge, and F96 measured the merge at only 4–6 % of wall time at 12
threads. The Mac's real advantage over the Fedora box is disk (539 GB vs 163 GB), not RAM.

**Do it in the GUI:** Docker Desktop → Settings → Resources → Advanced → Memory → Apply &
Restart. Suggested 12 GiB, leaving ~6 for macOS.

**Do not try the config file.** Adding `"MemoryMiB": 12288` to
`~/Library/Group Containers/group.com.docker/settings-store.json` (Docker Desktop 27.5.1,
SettingsVersion 41) was tried 2026-08-23: the key persisted but the VM still came up at
7.65 GiB, and Docker Desktop then exited and would not start again until the key was removed.
Removing it restored the daemon immediately with no other damage.

`tools/mac_run.sh`'s `-m` default is **8g** against the 11.67 GiB VM. Deliberately not higher:
a cap above the VM total does not fail cleanly (the VM OOM-kills the container), and the layer
files stream through the VM's page cache, which comes out of the same budget. 8g mirrors the
Fedora box, where run 4 sits at an 8G cap with ~3.2 GB anon and the rest page cache.

## 5. Keeping the Mac's engine in step (the real day-to-day hazard)

`third_party/smb-opt` is untracked; its only channel into this project is
`tools/smb-opt-modes.patch`, regenerated on the primary box at commit time. So **any pull that
changes that patch leaves the Mac's binary built from the wrong source**, and its numbers
silently wrong. This bit during this very session: the patch changed in `5bfe55c` while the Mac
still had the `2a1d15b` version applied.

Mechanised rather than left to prose:
- **`tools/mac_sync_engine.sh`** — hard-resets the clone to the pinned commit
  `daa4428`, reapplies the current patch, rebuilds in the container, and writes
  `third_party/smb-opt/.built-from` (patch sha256 + repo commit).
  The hard reset matters: the patch *adds* files, and if they were ever intent-to-added
  (`git add -N`) they count as tracked, `git clean` skips them, and the reapply fails with
  "already exists in working directory".
- **`tools/mac_run.sh` enforces it** — compares the patch's sha256 to the stamp and **refuses
  to run the engine binary** (exit 3) when they differ. `MAC_RUN_ALLOW_STALE=1` exists for the
  rebuild itself, not for getting a result out of a stale build.

### The control gate
After every resync, before trusting any Mac number:

```
tools/mac_run.sh -- third_party/smb-opt/target/release/smb-opt \
  bfscx W42Main data/wr/wr_inputs.bin 6584 575 587 --lift 0 --check-path 12
```

must reproduce `runs/P2.3c/ctrl_w42main_p575_d587.log` exactly:
**6, 16, 34, 70, 134, 673, 3472, 16472, 69489, 257001**.
Verified 2026-08-23 on commit `eae7ec2` — exact match. Native arm64 build: 1m 59s.

## 6. LAN — why a single search is never split across machines

```
ssh laptop "dd if=/dev/zero bs=1M count=600" | dd of=/dev/null bs=1M
629,145,600 bytes in 6.49 s = 96.9 MB/s  (~775 Mb/s; gigabit, saturated)
```

At F98's ~190 GB per full-level layer, moving one layer costs ~33 minutes. Distributed BFS
across the two boxes is therefore dominated by renting the F97 auction EPYC. Parallelism
across machines stays at the granularity of **whole independent jobs**.
