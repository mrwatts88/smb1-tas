# P2.3c-8 — Beam diversity (H39): the greedy beam was a per-layer seam, and F122 was its casualty

**Session 16, 2026-08-24.** Unit declared in STATUS "In progress". Origin: the user's argument that a
beam ordered by a single global key "essentially falls back to the greedy search by segment, because
we're getting rid of anything that you would pay for early to gain back later."

## 1. The argument (H39)

`bfscx --beam N` keeps the N lowest-h records per layer; `--beam-offset` keeps the N highest-offset,
then h. Both are **global single-key** orders. Any maneuver that must **pay before it gains** — slow
down, back off in x, drop height — has worsening h on exactly the layers it must survive, so it is
deleted before it can pay.

That is the same lossy operation as a first-arrival segment gate, applied **every frame** instead of
every seam. A beam does not escape segment-greedy search; it *is* segment-greedy search at 1-frame
granularity.

The engine already half-knew this. The `--beam-offset` comment reads: *"a minting maneuver costs
(slows, backs off x) before it pays, so h-first prunes it the instant it slows"*. The fix applied at
the time was a **second global key** — which only moves the blindness to another axis. Likewise the
seam protocol's step 3 ("reconstruct TWO candidates differing in vertical situation") is the same
insight applied by hand at width 2.

**Fix: a bucketed (diversity) beam.** Keep the best N *per physical bucket* over the axes a seam
hides in, never the best N overall.

## 2. The tool

`bfscx --beam N --beam-buckets <dims> [--beam-max M]` (engine, in the patch).

- `<dims>` is a comma list of `off` (scroll offset x − ScreenLeft16), `y` (16 px y band), `spd`
  (x-speed band), `sub` (x subpixel phase — F11/F37 subspeed dependence), `vf` (v_force, i.e. which
  airborne arc a state is on).
- `--beam N` becomes the **per-bucket** width when buckets are on.
- `--beam-max M` caps a bucketed layer: it shrinks the per-bucket width first (stays diverse) and
  only drops whole buckets as a last resort, printing a `WARNING capped` line when it does — so a
  partially-greedy run can never be mistaken for a diverse one.
- Helpers: `parse_beam_buckets`, `bucket_key` (`src/main.rs`).

**Regression (runbook §5): beam-off is byte-identical.** The `--lift 0` control gate
(`bfscx W42Main data/wr/wr_inputs.bin 6584 575 587 --lift 0 --check-path 12`) still gives layers
**6, 16, 34, 70, 134, 673, 3472, 16472, 69489, 257001**, goal at layer 10 (`runs/P2.3c-8/gate_beamoff.log`).

## 3. The test: re-run F122's frozen-offset probe

F122 concluded: *"the top route cannot mint the scroll offset the wrong warp requires… the offset
never leaves 112 across five searches… **No reachable input sequence mints any offset on the top
route.**"* Three of those five searches were beams. If H39 is right, they were blind to precisely
the pose a mint needs (integer speed 0, `moving_dir` LEFT, at a wall face).

Same root and deadline as F122's finale beams — `chain_s4v3.bin`, prefix **509**, deadline **72**,
`--enemies 0` — but the beam keeps the best **500 per bucket** over `off,y,spd,sub` (cap 3M) instead
of the best 2M overall:

```
smb-opt bfscx W42Main runs/P2.3c-2c/chain_s4v3.bin 6584 509 72 \
  --enemies 0 --threads 8 --acc-mb 96 \
  --beam 500 --beam-buckets off,y,spd,sub --beam-max 3000000 --log-offset \
  --layer-dir runs/P2.3c-8/f122_retest_layers
```

## 4. Result: the offset is NOT frozen — the top route mints +14 px

`runs/P2.3c-8/f122_retest.log`, 42.6 s, frontier ~180–220k/layer over ~550–650 buckets:

| layer | 1 | 29 | 30 | 34 | 36 | 37 | 38 | 39 | 40 | 41 | 42 | 43 | 44 | 46 | 69 |
|---|---|---|---|---|---|---|---|---|---|---|---|---|---|---|---|
| max offset | 112 | 113 | 114 | 115 | 116 | 117 | 118 | 119 | 120 | 121 | 122 | 124 | 125 | **126** | frontier dead |

A clean, near-monotone mint climb from 112 to **126** — **+14 px of the +20 the warp needs** — at
≈ **0.82 px/frame** over layers 29→46, which is *faster* than the bottom route's measured mint rate
of ~0.65 px/f (F123). The frontier then died at layer 69 because deadline 72 ran out, not because
the mint stalled.

**F122's central claim is refuted in the model.** The top route does mint.

### 4a. A second, independent weakness in F122's evidence

The two 509-root d72 beams that F122's table records as "offset 112" (`finale_beam2m.log`,
`finale_beam2m_off.log`) **contain no offset measurement at all** — `grep -c offset` = 0 in both;
the `--log-offset` print did not exist when they ran. Those two table rows were *inferred* from
"max x pinned at 0x530f0", not measured. Only `finale_beam484.log` (a different root, 484) actually
logged 112. So this run is the **first measurement of the scroll offset from the 509 root**, and it
reads 126, not 112.

## 5. Pushed further: the top route reaches 132 and enters the pipe

`runs/P2.3c-8/mint_d90.log` — same instrument, deadline 72 → 90 (479 s, frontier capped 3M):

| layer | 29 | 46 | 74 | 76 | 77 | 78 | 79 | 81 | 82 | 84 | 87 |
|---|---|---|---|---|---|---|---|---|---|---|---|
| max offset | 113 | 126 | 127 | 128 | 129 | 130 | 131 | **133** | 135 | 136 | 137 |

The 126 of §4 was **not** a ceiling — it was the deadline. At d90 the offset passes the warp's
**132** at layer 81 and the search reports **900 GOALs at layer 87** (records 7093..7179, i.e. a
4-2 main area of 509 + 87 = **596** frames — 8 slower than the WR's 588, 21 above the 575
one-framerule line; a beam upper bound, not an optimum).

**Core-verified.** Reconstructed (`warp87_path.bin`, 87 inputs), chained, replayed on QuickNES:
**87/87 frames, 0 mismatches**, core pipe entry GES 3 at record 7179 exactly as modelled. At that
frame the core reads **x 1348, ScreenLeft 1216, offset 132, AreaPointer $2F, EntrancePage 0** —
byte-identical to the WR's own entry condition.

## 6. But it warps to the wrong place — and the reason is a new fact (F129)

Running the core past the entry with Down held (F74):

```
frame   x   ScrLeft off  AreaPtr EntPage GES
 7177  1348  1216  132   0x2f     0     3   <- entry, WR-identical
 7178  1348  1218  130   0x2f     0     3
 7179  1348  1220  128   0x42     8     3   <- threshold crossed, wrong destination
```

The scroll **keeps advancing during the descent** and crosses the 1217 parse threshold two frames
in. Mario re-enters at x 1396 on ScreenLeft page 4 — not x 24 on page 0 (runbook §4.3).

The WR does not do this. Its RAM at entry:

```
        off  sct  Player_X_Scroll  ScrollAmount
WR    : 132   0         0               0        <- and 0 for the whole descent, offset pinned 132
ours  : 132   0         2               2        <- keeps applying, offset decays 132->130->...->107
```

**So the warp needs a second condition nobody had modelled: `Player_X_Scroll` = 0 at the entry
frame.** The WR's offset is a *latch* (F120's collision-push); the sct-frozen-running mint the top
route uses is *transient* — the scroll catches up the moment the timer lapses. F129.

**This makes the case goal under-constrained** — the same class of bug as F120. `goal_refused`
(`main.rs`) tests only `screen_left16 >= 1217` at the goal transition. It must also require the
entry frame to advance Mario's integer x by 0; the model already computes that (`emu.rs:388`,
`x_scroll`). **Until that lands, every wrong-warp GOAL the engine reports is suspect, including
these 900.**

## 7. What this does and does not establish

- **Does:** H39 is confirmed (F128) — a single-key beam is a per-layer first-arrival gate, and it
  cost this project a wrong verdict. F122's central claim is refuted (F127): the top route mints,
  reaching **offset 132** and a real pipe entry, core-verified. Its "structurally infeasible /
  mints nothing" framing is withdrawn. And F129 is a genuinely new mechanism fact about the warp.
- **Does not:** produce a record. 596 > 588 > 575, and the destination is wrong anyway. The top
  route is **not** shown to be capable of a *valid* warp — only of reaching the offset. Whether it
  can enter *stopped* at x 1348 (and what that costs) is now the open question, and it is the same
  speed-pricing question F123 answered for the bottom route.
- **Method note:** the searches here are beams — lossy, heuristic. A beam that finds something
  proves existence; a beam that finds nothing proves nothing (no-impossibility rule).
